# 内存优化指南

> 背景：后端 `code/backend/server_py` 单进程启动后内存占用过高。
> 根因主要是 **启动链路 eager import 了全部业务模块**，且部分模块在 **import 时就加载 AI 模型 / 重型原生库**。
> 本指南先给定位方法，再给按收益排序的优化手段，最后附立即可做的清单。
> **基线说明**：torch/transformers/spacy/nltk/pymilvus/neo4j/docling/ultralytics 等重型依赖已随模块裁剪从 pyproject 移除，主进程内存压力已大幅缓解；本文方法论保留，用于内存回归排查与新依赖引入评估。

## 1. 内存都花在哪了

### 1.1 启动链路：全模块 eager import

[app.py](../../../code/backend/server_py/src/app.py) 在顶层 import 了全部保留模块（module_ai、module_office、module_rag、module_task 等），Python 的 import 是级联的——每个 controller 会拉起 service → dao → utils 的完整依赖链。任何一个 utils 顶层 import 了重型推理库，主进程就背上相应的常驻内存。

### 1.2 重型依赖现状（[pyproject.toml](../../../code/backend/server_py/pyproject.toml)）

基线已随模块裁剪从 pyproject 移除的重型依赖：

| 类别 | 已移除依赖 | 原典型常驻内存 |
| :--- | :--- | :--- |
| LLM/Embedding | torch、transformers、sentence-transformers、peft | 数百 MB～数 GB（含模型权重） |
| 文档解析 | docling、pypdfium2 | 数百 MB |
| NLP | spacy、nltk | ~100 MB |
| 向量库/图谱 | pymilvus、neo4j driver | 连接 + 数据缓存 |
| 视觉 | ultralytics（YOLO，连带 torch） | 数百 MB |

基线保留、仍需关注的中重型依赖：

| 类别 | 依赖 | 说明 |
| :--- | :--- | :--- |
| 语音 | soundfile | 在线 ASR/TTS 的音频解码与重采样（本地引擎已移除） |
| OCR/视觉 | opencv-python-headless、pillow | 图像预处理（已换 headless 版去掉 GUI 依赖；cv2 在 OCR 接口内惰性 import，启动不加载） |
| 向量库 | pymilvus（当前使用） | 远程 milvus 后端；lancedb 为本地备选（可选依赖按需安装，未安装时启动不受影响） |
| LLM 编排 | langchain 全家桶、langgraph-checkpoint-postgres | 数十～数百 MB |

### 1.3 import 时即执行加载的点

- 基线已清理顶层重型 import：torch/transformers/spacy/docling/ultralytics 的顶层加载点已随依赖移除；module_rag 对 module_office 解析/切分服务的引用均在函数体内惰性 import，方向正确。
- cv2（opencv）已同样下沉：`common/utils/media/file_format.py` 与 `module_ai/utils/ocr/dashscope.py` 均为函数内 import，实测 `import app` 后 `sys.modules` 无 cv2——主进程 RSS 由约 411MB 降至约 279MB（-32%）。
- 仍需保持的约定：重依赖（langchain 系/lancedb/babylon 级别）维持**函数内按需加载 + 单例工厂**，新增能力不得回退为顶层 import。
- 排查方法不变：`python -X importtime` 日志按模块名检索，或在 memray 火焰图定位 import 阶段分配大头。

## 2. 定位方法：先测量再优化

```bash
cd code/backend/server_py

# 1) 看各模块 import 耗时与顺序(间接反映 import 链)
$env:PYTHONPATH="src"; python -X importtime src/app.py 2> import.log

# 2) 用 memray 定位 import 阶段的内存分配(uv add --dev memray)
$env:PYTHONPATH="src"; python -m memray run src/app.py
memray flamegraph memray-src.app.py.<pid>.bin
```

- 火焰图里找 **import 阶段**（服务启动前）的分配大头，通常是 `torch/transformers/onnxruntime` 的原生库初始化。
- 运行期增长用 `tracemalloc` 快照对比，或直接访问已有的 `/server-status`（基于 psutil 的服务状态接口）观察 RSS 曲线。
- 判断某模块是否被主进程拉起：`python -c "import sys; ..."` 前置模拟，或直接在 import.log 中搜模块名。

## 3. 优化手段（按收益排序）

### 3.1 惰性导入重型模块（收益最大，不改架构）

原则：**controller → service 的链条只允许出现轻量依赖；torch/transformers/onnxruntime/spacy/docling 只允许出现在函数体内。**

```python
# 反例: 顶层 import, import 即加载重型模型（示意）
from module_ai.utils.voice.tts import SherpaTTS

# 正例: 使用时才加载
def get_tts() -> "SherpaTTS":
    from module_ai.utils.voice.tts import SherpaTTS  # 函数内 import
    return SherpaTTS.get_instance()
```

- FastAPI 路由注册不依赖 utils 的顶层 import，函数内 import 对启动耗时也无影响（首次请求略慢，可接受）。
- 语音/OCR 模型加载器如出现新的顶层 import，一律改为 `get_xxx()` 惰性单例。
- 注意：不要用 `lru_cache` 包住异步/带参对象以外的重模型加载器以外的东西过多，模型加载器统一走"模块级 `_instance` + 双检锁"或项目已有的 dependencies 工厂模式（参考 [dependencies/status.py:3-5](../../../code/backend/server_py/src/module_main/dependencies/status.py#L3-L5) 的软单例写法）。

### 3.2 模型单例 + 显式生命周期

模型实例必须全局唯一、按需创建、可主动释放：

```python
class SherpaTTS:
    _instance = None

    @classmethod
    def get_instance(cls) -> "SherpaTTS":
        if cls._instance is None:
            cls._instance = cls()   # 首次调用才 OfflineTts(cfg)
        return cls._instance
```

- 同一份模型禁止在多个 service 中各加载一次（YOLO predict/train、OCR 各子模型、embedding 模型都要收敛到单例工厂）。
- 提供统一的 `release()`（del 模型引用 + `gc.collect()`），用于低峰卸载或切换模型。

### 3.3 进程拆分：主服务轻量化，重 AI 独立部署

最彻底的方案：把重 AI 推理（module_ai 语音/OCR 模型）拆成独立 FastAPI 服务（独立进程、独立内存上限），主服务通过 HTTP/内网调用；文档解析已外部化（MinerU 远程服务调用，无本地推理），一般无需独立进程。

- 主服务（路由 + DB + RAG 编排）内存可降到几百 MB 量级。
- 重服务可单独重启/限流/漂移，不影响主服务可用性。
- 过渡方案：先用环境变量开关（如 `ENABLE_HEAVY_MODULES=false`）让 app.py 跳过 module_ai 的 import，验证收益后再拆分。

### 3.4 推理配置降档

- 基线已无本地推理（asr/tts/ocr 全走在线服务），本节保留给后续接入本地推理时参考：onnxruntime 用 `SessionOptions` 限制线程与内存（`intra_op_num_threads`、`enable_mem_pattern=False`）、优先 int8 量化模型（体积与常驻内存通常降 60%～75%）。
- LLM 调用一律走 OpenAI 兼容远端/本地服务（基线无本地 transformers 推理），主进程只需关注 httpx 客户端复用与流式缓冲上限。

### 3.5 缓存与累积结构治理

- 项目已有 [ttl_cache](../../../code/backend/server_py/src/common/utils/cache/cache_ttl.py)（带 TTL 的方法缓存），新缓存一律用它或 `lru_cache(maxsize=N)`，**禁止无界 dict/list 当缓存**。
- 排查后台任务（[app_task.py](../../../code/backend/server_py/src/app_task.py)，celery `--pool=solo --concurrency=1`）与 SSE/WebSocket 会话中保存历史消息的结构，超过上限要落库或截断。
- langgraph checkpoint（postgres）保存的是状态而非内存，确认没有进程内重复缓存对话历史。

### 3.6 连接池与并发参数

- 数据库连接池（common/config/db.py）按实际并发设置 `pool_size`（如 5～10），不要默认拉满；每条连接在 asyncpg 侧约几 MB。
- httpx/aiohttp 客户端复用单例，避免每次请求新建连接池。
- uvicorn 单进程即可，不要盲目多 worker：每个 worker 都是完整 import 链，内存翻倍。

## 4. 立即可做的清单（Quick Wins）

1. [ ] 排查 app.py import 链中所有顶层重型 import（当前基线已清理；新引入依赖时必须下沉到函数内，重点：module_ai/utils、module_office/utils，cv2 惰性加载即范例）。
2. [ ] 用 `python -X importtime` 评估新增/低频模块是否值得从主服务剥离。
3. [ ] 新依赖接入前先回答「是否必须主进程加载 / 能否惰性加载」（参照 2026-10-17 实测：cv2 惰性加载使启动 RSS 降约 132MB）。
4. [ ] 全局搜索 `dict()`/`list()` 形式的模块级缓存，统一替换为 ttl_cache 或 lru_cache(maxsize=N)。
5. [ ] 验证：改造前后分别记录 `/server-status` 相关接口的 RSS 与 `python -X importtime` 日志，形成基线对比。

## 5. 长期约定

- 新增重型依赖前，先回答两个问题：**是否必须主进程加载？是否可以惰性加载？** 两者答案都为"是"时才允许顶层 import。
- code review 检查项：controller/service 禁止顶层 import AI 推理库；模型加载必须走单例工厂。
- 每个模块的 README/文档标注其重型依赖，便于评估部署内存预算。
