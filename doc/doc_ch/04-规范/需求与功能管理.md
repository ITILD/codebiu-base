# 需求与功能管理

> 一句话规则：**先登记 → 人批准 → 再开发 → 交付登记**。状态不是「已批准」就不写功能代码。
> 台账：[00-需求功能登记册.md](../03-设计文档/00-需求功能登记册.md)　卡片模板：[99-需求卡模板.md](../03-设计文档/99-需求卡模板.md)

## 1. 状态（只有 4 个）

```
草案 ──人批准──→ 已批准 ──过验收──→ 已交付
 └──────────────────→ 已废弃
```

| 状态 | 含义 | 能否开发 |
| :--- | :--- | :--- |
| 草案 | 已登记，卡已填，等人点头 | ❌ |
| **已批准** | 用户明确批准（回复"同意/可以/批准"均算） | ✅ **唯一可开发** |
| 已交付 | 验收标准全部勾选，登记册已同步 | — |
| 已废弃 | 不做了（编号保留不复用） | ❌ |

**批准 = 一次对话确认**。不要求会议、不要求正式评审文档；卡里的「影响面 / 方案 / 验收标准」就是全部评审材料。

## 2. 编号（递增不复用）

| 概念 | 编号 | 说明 |
| :--- | :--- | :--- |
| 需求 REQ | `REQ-<NNN>` | 一次业务诉求 = 一张卡（如 REQ-005） |
| 功能 FEAT | `FEAT-<域>-<NNN>` | 卡内一条可独立验收的功能（如 FEAT-AGENT-001） |

域（全大写缩写）：`BASE` 基线公共 / `AGENT` 智能体 / `CADGIS` 二三维 / `NOVEL` 小说站 / 新场景自定义。

## 3. 日常只有 4 个动作

| 动作 | 谁做 | 怎么做 |
| :--- | :--- | :--- |
| 登记 | AI 自动（人可手动） | 复制模板到 `03-设计文档/requirements/REQ-<NNN>-<短名>.md` 填卡 → 登记册加行 |
| 批准 | **人（唯一必做动作）** | 看卡 → 回复批准 → 状态改「已批准」（记日期） |
| 开发 | AI / 人 | 按 [开发流程.md](开发流程.md) 实现，遵守 [代码规范.md](代码规范.md) |
| 交付 | AI / 人 | 验收标准逐条勾选 → 状态改「已交付」→ 卡补交付记录 |

## 4. AI 默认流程（用户提需求后 AI 全自动走）

```
用户提需求 → ① AI 填卡 + 登记册加行（草案）
           → ② AI 给出功能清单/方案/验收标准，请求用户批准
           → ③ 用户批准 → 状态改「已批准」→ 按《开发流程》开发
           → ④ 验收通过 → 状态改「已交付」→ 补交付记录
```

信息不足时 AI 先问再登记；用户直接说"批准"即可推进，其余全部 AI 代办。

**AI 禁例**：没登记就写功能代码；自己替用户批准；验收标准没全过就置「已交付」；在基线公共模块里硬编码场景专有逻辑。

## 5. 豁免（不占编号）

缺陷修复、文档更新、纯重构（不改行为）、依赖升级 → 只在登记册「[变更记录](../03-设计文档/00-需求功能登记册.md)」表加一行，无需开卡。

## 6. 基线保护

动公共层（`common/`、module_main、module_authorization 等）的需求，卡里必须写明影响面与兼容说明；优先以**新增模块/新增文件**扩展场景，不为单场景需求修改公共底座。
