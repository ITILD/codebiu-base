# 文档代码同步巡检

## 何时使用

每周定期、发版前、外部代码合入后、人员交接前；或用户反馈「文档和代码对不上」。

## 执行步骤

### 1. 定范围

- 默认：最近 7 天变更 + 未提交改动。
- 发版前：自上个版本 tag 至今。
- 全仓库：首次接手或大版本重构后。

```bash
git log --since="7 days ago" --name-only --pretty=format:"%h %ad %s" --date=short
git status --short
```

### 2. 代码侧检查

1. 收集变更文件，按端与层级归类。
2. 找 `@doc-sync` 标记：

```bash
rg -n "@doc-sync" code/
```

3. 校验每个标记：
   - 指向的文档路径存在。
   - 文档中确实描述该代码的职责。
   - 代码改了但标记未更新 → 高危。
4. 检查新模块是否注册：后端 `src/app.py`、前端 `menu.ts`、客户端功能卡片。

### 3. 清单侧检查

打开 [`doc/doc-manifest.yaml`](../doc-manifest.yaml)：

- 每个 `path` 存在。
- 每个 `code` 路径存在（删除的代码要清理映射）。
- 新增模块/能力有对应条目。
- `mirror` 指向的文件存在且结构一致。

### 4. 文档侧检查

1. **链接**：抽查本文件与 [doc/README.md](../README.md) 的全部相对链接；可用 `rg -o '\]\(([^)]+\.md[^)]*)\)'` 提取后逐个确认。
2. **双语**：`README.md` 与 `README.en.md` 的章节标题数量、截图路径、链接目标一致。
3. **单一来源**：同一规则是否在两层重复；重复则保留归属层，另一处改链接。
4. **登记册一致性**：需求状态「已交付」但需求卡未勾验收 / 文档未更新 → 高危。

### 5. 分级与处理

| 级别 | 判定 | 处理 |
| :--- | :--- | :--- |
| P0 高危 | 接口/表/权限/契约与文档不一致；`@doc-sync` 失效 | 立即修复，不能发版 |
| P1 中危 | 模块清单、目录、配置项过期；双语文案不一致 | 本次迭代修复 |
| P2 低危 | 链接失效、措辞过期、示例过时 | 排期修复 |

### 6. 输出报告并留痕

报告写到对话或需求卡交付记录；涉及文档修复的，在登记册「变更记录」加一行。

## 输出模板

```markdown
巡检范围：<时间/commit/全仓库>
巡检时间：<YYYY-MM-DD>

| 级别 | 位置 | 漂移描述 | 应改文档 | 处理 |
| :--- | :--- | :--- | :--- | :--- |
| P0 | <代码/文档> | <不一致点> | <path> | 已修复/待办 |

统计：P0 <n> / P1 <n> / P2 <n>
结论：<可发版 / 需修复后发版>
```

## 禁止事项

- 只跑链接检查，不核对代码事实。
- 发现漂移后只改文档、不确认代码是否有意变更。
- 把 P0 漂移留给「下次再说」。
- 巡检后不在登记册留痕。

## 自检

- [ ] 巡检范围明确
- [ ] `@doc-sync` 标记全部有效
- [ ] `doc-manifest.yaml` 无失效路径
- [ ] 双语与链接检查完成
- [ ] 分级合理，P0 已修复或有阻塞说明
- [ ] 已留痕
