## 0. 结论摘要（TL;DR）

1. **平台只认三种一等公民**：`Model`（能力供给）、`Skill`（能力单元）、`Agent`（编排单元）。任何新功能先归类（§2.6 判定树）：普通业务 CRUD 仍走 `Controller → Service`；需要被对话调用、需要入队、需要跨模块复用的能力包成 Skill；多步编排上升为 Agent。
2. **每一层都有 ai / static 双形态**（基线核心抽象，贯穿三层）：
   - Model = `ai_model`（大/小模型：chat/embeddings/rerank/ocr/asr/tts）+ `static_func`（固定规则函数：对现实规则和业务建模，哈希、格式识别、正则抽取、校验器）
   - Skill = `ai_skill`（依赖模型）+ `static_skill`（纯规则/流程/算法）+ `hybrid`（规则主干+局部模型）
   - Agent = `ai_agent`（ReAct 自主找 skill 和 model 解决问题）+ `static_agent`（LangGraph 固定工作流）+ `hybrid`
3. **不强制使用 AI**：`static_*` 能力在零模型配置环境必须可运行；规则能力与 AI 能力在契约、队列、治理上完全平权。Model 层不是平台的前置条件。
4. **依赖单向**：`Agent → Skill → Model(可选) → Service`；Model 不调用任何东西；Skill 之间不互相编排（组合只发生在 Agent 层）；领域逻辑、事务、DAO 留在 Service。
5. **三个平行入口共用一个运行时**：Web Controller（页面手动触发）、Agent Tool Adapter（对话中自动匹配调用）、Task Executor（推到 Celery 排队）全部汇合于 `SkillRuntime.invoke()`，同一 Skill 只有一份业务实现，inline / queued 只是两种外壳。
6. **首个落地样板**（即需求举例）：`doc_parse`（文档解析，输出 markdown + 结构块两种产物）+ `doc_chunk_index`（分块入库）两个 Skill。批处理场景由 `kb_ingest_agent`（static_agent，LangGraph 固定工作流）编排两步；对话场景由问答 ai_agent **直接编排两个 Skill 句柄**（Agent 调用 Agent 被最终禁止，CA-02）；页面通过 Controller 手动触发某知识库某文件的解析入库；三条路径都可推到 Celery 执行。
7. **执行双形态**：`inline`（进程内、秒级、硬超时）与 `queued`（Celery、长任务、可进度/取消）；由 SkillRuntime 按 Skill 声明 + 输入规模自动选择，不由调用方决定。
8. **统一观测**：每次调用（无论哪条入口、哪种形态）写 `skill_invocation`；queued 调用与 `task_queue` 通过 `task_id` 双向关联。

## 1. 设计动机与现状差距

### 1.1 为什么以 AI 为中心重新抽象

基线项目的价值在于**新项目复制即得一套可扩展的 AI 平台底座**。当前能力组织是「接口 + 业务服务」式的：解析、分块入库、问答各自绑定在特定 Controller 和 Celery 任务上，问答侧的 Agent 又只有 4 个只读技能——平台最重的几个能力反而在 Agent/Skill 抽象之外。下一代平台的答案是：**把能力本身做成平台资产**（可注册、可声明、可编排、可观测、可治理），业务功能退化为对这些资产的组合与触发。

### 1.2 现状盘点（2026-11 代码基线）

| 现状 | 位置 | 与目标的差距 |
|---|---|---|
| 模型配置（chat/embeddings/rerank/ocr/asr/tts，public/dept/user 三作用域 + is_default） | `module_ai` ModelConfig / `model_config.py` | ✅ 已是 Model 层雏形；缺 `static_func` 一种、缺能力绑定声明 |
| 技能注册表 `SkillDef`（name/description/args_model/func）+ 4 个只读技能（web_search/ocr_image/file_search/kb_qa） | `module_agent/skills/` | 只是 chat Agent 的 tool 列表：无 Manifest 契约、无执行形态、无观测、`capability` 仅 read/write |
| 文档解析（MinerU remote/local，ParserFactory 可扩展） | `module_office` | 是接口+服务，不是可被对话/队列/页面三入口复用的 Skill |
| 解析+分块+向量入库一体化任务 `reparse_document_task` | `module_rag/tasks/` | 三步耦合在一个 Celery 任务里，无法单独复用解析或入库；没有 Agent 编排概念 |
| 双引擎任务队列（local 进程内 / celery worker）+ task_queue 表 | `module_task` | 队列按业务功能注册任务类型，新增能力就要改注册表；无资源域、无优先级语义 |
| RAG 问答（LangGraph + ag-ui SSE 流式） | `module_rag` rag_chat | 问答图与能力层无契约关联，附件「解析中」链路未抽象 |
| 智能体（agent 表 + skills 多选 + 系统提示词） | `module_agent` | 只有 chat 一种形态；无 static_agent / 工作流编排 |

### 1.3 核心问题表

| 问题 | 影响 |
|---|---|
| 能力 = 接口 + 业务服务，不可复用 | 问答附件、知识库导入、重解析各写一套调用逻辑，行为不一致 |
| 最重的能力在抽象之外 | 解析/入库走专用 Celery 任务，对话 Agent 调不到它们 |
| 队列以业务功能注册 | 新能力要改任务注册表 + worker；交互等待与夜间批量同池竞争 |
| 是否依赖模型是隐式的 | 换模型容易漏配，运行期才报错 |
| 无统一调用记录 | 无法回答「这个能力被谁调用、耗时、失败率、token 成本」 |
| 规则类能力无处安放 | 格式转换、去重、归档被硬塞进 prompt 或重复写脚本 |

## 2. 核心抽象：三层一等公民

### 2.1 层级关系

```text
抽象小、原子性强 ──────────────────────────▶ 抽象大、面向完整任务
┌────────────────────────────────────────────────────────────────┐
│ Agent 编排层：完成一整套任务的工作流或角色                        │
│   ai_agent(ReAct/plan-execute) │ static_agent(LangGraph 固定流) │ hybrid
│   例：kb_ingest_agent = doc_parse → doc_chunk_index 编排         │
├────────────────────────────────────────────────────────────────┤
│ Skill 能力层：单一工作技能（最小可复用执行单元）                    │
│   ai_skill │ static_skill │ hybrid                              │
│   例：doc_parse（双产物输出）、doc_chunk_index                    │
├────────────────────────────────────────────────────────────────┤
│ Model 供给层：基础能力供给（不含业务逻辑）                         │
│   ai_model(chat/embeddings/rerank/ocr/asr/tts) │ static_func    │
│   例：Qwen 主模型、MinerU 解析引擎(经 Skill 包装)、哈希/正则函数  │
├────────────────────────────────────────────────────────────────┤
│ Service 领域层：领域逻辑/事务/权限过滤/DAO（既有，不变）            │
└────────────────────────────────────────────────────────────────┘
调用链唯一：Agent → Skill → Model(可选)/Service → DAO
```

三个正交维度，互不推导、必须分别声明：

1. **主体**：Model / Skill / Agent
2. **能力来源**：static（deterministic）/ ai / hybrid —— 每层都有，语义见 §2.2~§2.4
3. **执行形态**：inline / queued —— 只在 Skill 层声明（§4.2）

### 2.2 Model 层：能力供给（ai_model + static_func）

Model 只描述「能提供什么能力」，不承载业务逻辑，不感知 Skill/Agent，不可调用任何东西。

| 子类 | 定义 | 注册方式 | 示例 |
|---|---|---|---|
| `ai_model` | 外部/在线推理服务接入的模型能力 | `model_config` 表（既有）：`model_type` ∈ chat/embeddings/rerank/ocr/asr/tts/image，`scope`(public/dept/user) + `is_default` 三作用域解析链保留 | Qwen chat 主模型、bge embeddings、paddle OCR |
| `static_func` | **对现实规则和业务建模的固定规则函数**：纯函数、同输入必同输出、零外部副作用 | 代码注册表 `module_ai/functions/`（pydantic 声明签名 + 实现引用，v1 不入库） | 文件类型嗅探、内容哈希、正则抽取（邮箱/手机号/日期）、表格行列校验、金额格式化 |

设计要点：

- **static_func 与 ai_model 平权**：同一个能力注册表、同一种解析入口（`capability_registry.resolve(capability_key, ctx)`）；Skill 的 `model_bindings` 既可以绑 ai_model 也可以绑 static_func。
- **为什么 static_func 放 Model 层**：它和 ai_model 一样是「被绑定的供给品」——Skill 声明「我需要一个文档类型识别能力」，运行时解析到 LLM（ai 路线）或 `mime_detect` 函数（static 路线），Skill 实现不感知差异。这正是「对现实规则建模」的落点。
- **分块策略选择、检索融合、去重合并不是 Model**：它们含流程/业务语义，属于 Skill 层（§3.4 什么不是 Model 同参考文档 §3.4 精神）。
- 外部解析服务（MinerU）经 Skill 包装暴露，不在 Model 层直接暴露。
- **平权不等于同质**：两类供给在契约上按类显式分叉，避免「统一得太粗掩盖差异」：

| 契约项 | ai_model | static_func |
|---|---|---|
| 超时 | API 超时可配 | **不设超时**（纯函数无外部等待） |
| 失败模式 | 网络/限流/鉴权（transient 居多） | 计算错误（permanent 居多） |
| 成本计量 | tokens + 时长 | CPU/时长（tokens 恒 0） |
| 版本与生命周期 | `model_config`（DB 变更） | 代码注册表（随 git 版本） |
| 缓存语义 | 不缓存（除非显式声明） | 同输入必同输出，允许按签名缓存 |

- **双源合并规则**：能力注册表 = `model_config`（DB）∪ `module_ai/functions/`（代码），启动时同步并做一致性校验（key 冲突/声明漂移即启动失败）；resolve 入口唯一。
- **纯函数约定（static_func）**：实现禁止任何 I/O（网络/文件/DB），同输入必同输出；由单元测试约定把关（测试内 monkeypatch 网络/文件 API 断言未被触碰），契约层不做运行时校验。

### 2.3 Skill 层：单一工作技能

Skill 是 **Service 之上的工具技能层**：稳定 `key`、输入/输出 Schema、幂等键、执行模式、能力声明；可以完全依赖模型（ai_skill）、完全不依赖模型（static_skill）、或规则主干+局部模型（hybrid）。

| `nature` | 含义 | 依赖模型 | 模型缺失时 | 典型 |
|---|---|---|---|---|
| `static_skill`(deterministic) | 纯规则/流程/算法 | 否 | 正常运行 | 文件格式转换、去重、固定分块、归档 |
| `ai_skill`(ai) | 必须模型参与 | 是 | `capability_missing` 快速失败 | 摘要、意图识别、AI 打标、语义分块 |
| `hybrid` | 流程为主，模型可选/局部 | 可选 | 必需能力缺失则失败；可选能力缺失降级并标 `degraded=true` | 文档解析（OCR 可选）、分块入库（策略识别可选 + embeddings 必需） |

规则（承接参考文档 AS-17/18 的基线裁剪）：

1. `nature` 是**必填声明**，不是运行时推断。
2. `static_skill` 必须能在零模型配置环境运行。
3. `hybrid` 必须声明降级策略；不允许「模型不可用就整体失败」。
4. Skill 实现保持薄：编排一个或多个 Service 调用，禁止绕过 Service 直接操作 DAO/开事务（领域逻辑在 Service，AS-21 精神）。
5. Skill 之间不得互相调用；组合上移到 Agent 层。

### 2.4 Agent 层：完成一整套任务的工作流或角色

Agent 是编排单元，本身不实现业务能力；「Agent 的本质是编排，不是模型」——即使所有步骤都是 static_skill、全程不调用任何 LLM，它仍然是有效的 Agent。

| 形态 | 对应用户定义 | 决策方式 | 运行时 | 示例 |
|---|---|---|---|---|
| `ai_agent` | 自己 ReAct 找 skill 和 model 执行解决问题 | `decision_mode=model`：模型决定下一步（execution_strategy ∈ direct/react/plan_execute） | Web 进程 LangGraph + SSE 流式 | 问答 Agent、深度研究 Agent |
| `static_agent` | langgraph 的固定工作流 | `decision_mode=rule`：步骤、分支、依赖全部显式声明，禁止模型自由选择 | Celery worker（job 形态）或进程内（轻量 job） | `kb_ingest_agent`、定时归档 Agent |
| hybrid | 固定骨架 + 模型节点 | `decision_mode=hybrid`：主干按 steps 执行，仅 `model_node: true` 步骤内允许单次 direct 调用 | 同上 | 知识库构建（分块策略识别/AI 打标步骤用模型） |

Agent 两形态 × 三决策的组合语义：

| | chat（会话流式） | job（批处理编排） |
|---|---|---|
| 默认 decision_mode | model / hybrid | rule / hybrid |
| 能力调用 | tool-calling 只暴露 `agent_callable=true` 的已发布 Skill | 步骤编排调用 Skill，可 `fan_out` 并行展开 |
| 状态 | 会话状态入 checkpointer（既有） | `agent_job_run` + 步骤状态落库，断点续跑 |
| 长耗时 Skill | 返回句柄 `{invocation_id, status: pending}`，图内 await 轮询 | 天然 queued，聚合子任务进度 |

job 编排能力边界（最终设计）：**线性 steps + fan_out + depends_on + 批内条件**——`when`（步骤级准入表达式）/ `skip_if`（fan_out 展开项过滤，如「降级产物不得自动入库」在编排层表达，见 §3.3）；动态依赖、循环、子工作流、Agent 嵌套不引入。Agent 嵌套即 Agent 调用 Agent，**最终设计确认禁止**（CA-02）：对话场景由 ai_agent 直接编排 Skill 句柄（§4.4），批处理场景由 static_agent steps 编排（§3.3）——避免把调度器做成通用工作流引擎。

### 2.5 依赖与组合规则（关键不变量）

| 编号 | 不变量 |
|---|---|
| CA-01 | 新功能必须归类为 Model / Skill / Agent 之一（业务 CRUD 与展示除外） |
| CA-02 | 依赖方向只能 `Agent → Skill → Model(可选)`、`Skill → Service`；禁止 Model 调用 Skill、Skill 调用 Agent、**Agent 调用 Agent（最终确认禁止，无过渡形态）**——对话场景 ai_agent 直接编排 Skill 句柄，批处理场景 static_agent 编排 Skill |
| CA-03 | 每个 Skill 必须声明 input_schema / output_schema / idempotency keys |
| CA-04 | 同一 Skill 的 inline 与 queued 复用同一业务实现，禁止两份逻辑 |
| CA-05 | inline 必须有硬超时；超过输入阈值的调用必须转 queued |
| CA-06 | static 能力（static_func / static_skill / rule Agent）必须零模型可运行 |
| CA-07 | 确定性能力不得被强制走 LLM；rule Agent 分支条件必须是显式表达式 |
| CA-08 | Skill/Agent 只能拿到调用上下文授权范围内的资源（project_ids/user_id 由运行时注入，不得自行扩大） |
| CA-09 | 运行中的 Agent/Skill 固定版本快照，不因后台编辑漂移 |
| CA-10 | queued 调用必须先落 `task_queue` 再投递 Celery（沿用 module_task 既有不变量） |
| CA-11 | 所有调用写 `skill_invocation`，失败必须带 `error_class` |
| CA-12 | 成本/超时预算耗尽必须优雅降级并返回可解释结果，不得无限重试 |

### 2.6 新功能归类判定树

```text
Q1 只是接入/配置/调用某个模型或固定规则函数？
   ├─ 是 → Model（model_config 加模型 / functions 注册表加函数，不新增业务代码）
   └─ Q2 单次、无状态、输入输出明确、可被多处复用的执行单元？
      ├─ 是 → Skill（声明 nature：static / ai / hybrid）
      └─ Q3 需要多步骤编排或会话上下文？
         ├─ 是 → Agent（步骤固定无模型 → static_agent；每步模型决策 → ai_agent；骨架+模型节点 → hybrid）
         └─ Q4 业务实体流转、人工审批、权限管理？
            ├─ 是 → 业务流程（其中可复用执行动作下沉为 Skill）
            └─ Q5 普通 CRUD/展示/统计 → Controller + Service，不进入三层抽象
```

典型归类：

| 功能 | 归属 | 来源/决策 |
|---|---|---|
| 新增 Qwen 推理模型 | Model(ai_model) | 只加 model_config |
| 内容哈希、文件类型嗅探 | Model(static_func) | functions 注册表 |
| 文档解析（markdown+结构块双产物） | Skill(`doc_parse`) | hybrid |
| 分块+向量化入库 | Skill(`doc_chunk_index`) | hybrid |
| 知识库整库解析入库 | Agent(`kb_ingest_agent`) | rule（static_agent） |
| 问答 | Agent(chat) | model（ai_agent） |
| 接入社区 SKILL.md 包 / MCP server | Skill（经适配器） | W-14：加载器拆解/adapter 反射注册为 Skill，不新增第四层 |
| 审核员工作台 | 业务流程 | 打标 Skill 只提供建议 |

## 3. 契约规范

### 3.1 Skill Manifest（契约核心）

内置 Skill 由各业务模块的代码 Manifest 声明（`module_xxx/skills/<key>/manifest.py`），数据库只做只读同步；用户自定义 Skill（后续批次的 prompt 类型）才走 `ai_skill`/`ai_skill_version` 表。

```yaml
namespace: sys                # sys 内置 / usr 用户自定义 / pack.{包名} 社区包 / mcp.{server}（W-14）；key 唯一性 = namespace.key（W-7）
key: doc_parse
name: 文档解析
description: 将文件解析为 Markdown 与结构块两种产物
category: ingest              # ingest / retrieval / generation / governance / action
skill_type: builtin_tool       # 全枚举：builtin_tool/prompt/python_script/script/mcp_tool（W-15 一步定义全）；首批仅交付 builtin_tool
nature: hybrid                 # static / ai / hybrid
impl_ref: module_office.skills.doc_parse.impl:run

input_schema:
  required: [source]
  properties:
    source: {type: object}     # {kind: upload|file_id|url, ref}
    document_id: {type: string}
    options: {type: object}    # ocr: auto|on|off
output_schema:
  properties:
    markdown: {type: string}   # 产物一：整篇 Markdown
    blocks: {type: array}      # 产物二：文档结构小块（含层级/页码/表格定位）
    meta: {type: object}       # parser/ocr_used/warnings

required_capabilities: []      # 为空 = 不依赖模型也能跑（hybrid 主干）
optional_capabilities: [ocr]  # 缺失时降级
capability_alternatives: []   # 可选能力组，如 doc_chunk_index：[[embeddings],[store:bm25]]（W-6），至少一组可满足即可发布
model_bindings: {}              # 能力 → {model|func, policy}

execution:
  modes: [inline, queued]
  inline_timeout_s: 60
  queued_timeout_s: 1800
  resource_domain: parse        # parse / index / llm / none（队列白名单，见 §4.3）
idempotency:
  keys: [document_id, content_hash, parse_config_hash]
progress: true
cancel: true
retry: {max: 2, backoff_s: 30}
side_effects: write             # none / read / write / external
agent_callable: true           # 是否暴露给 ai_agent 的 tool-calling
```

校验规则（发布/同步时）：

- `nature=static` 时 required/optional capabilities 与 model_bindings 必须为空。
- `nature=ai` 时 required_capabilities 不得为空；显式绑定的模型必须存在、启用、`model_type` 与能力一致。
- `hybrid` 必须为每个 optional capability 声明降级行为。
- `capability_alternatives` 声明后：至少一组全部可解析才可发布/同步；运行时按组解析，全部不可满足 → `capability_missing`，落到降级组则 `degraded=true`。
- key 唯一性按 `{namespace}.{key}` 判定；内置固定 `sys`，用户自定义默认 `usr`（W-7）。
- 无进度上报的 Skill 不得声明 queued（CA-05）。

### 3.3 Agent 配置（static_agent 样板）

```yaml
key: kb_ingest_agent
name: 知识库文档入库
agent_kind: job
decision_mode: rule            # static_agent：无模型
steps:
  - id: parse
    skill: doc_parse
    fan_out: documents         # 按文档列表并行展开
    on_error: collect          # 单文档失败不阻塞其他（collect / fail_fast）
  - id: index
    skill: doc_chunk_index
    depends_on: [parse]
    fan_out: documents
    skip_if: "parse.degraded == true"   # 展开项级过滤：降级产物不得自动入库（批处理编排层表达，W-2）
runtime_policy:
  queue: q_agent_job            # 批处理物理队列（§4.3）
  priority_class: batch
  max_parallel: 8
  budget: {max_duration_s: 7200, max_tokens: 1000000}
```

执行语义：每步生成一批 Skill 调用按 `fan_out` 展开；**批内条件在编排层表达**——`when` 为步骤级准入表达式（引用前序步骤输出字段），`skip_if` 为展开项过滤（如 `parse.degraded == true` 的文档跳过 index 步）；条件必须是显式表达式（CA-07），禁止塞进 Skill 实现隐藏。幂等 = 同 `job_run_id + document_id + step_id` 只执行一次（载体 `agent_job_run`，§6）；进度 = 完成文档数/总数；断点续跑靠步骤状态落库。chat Agent（ai_agent）继续沿用现有 LangGraph 问答图，工具清单从 Skill 注册表生成（仅 `published` + `agent_callable=true`）。

|---|---|
| invalid_input | 不重试 |
| capability_missing | 不重试，发布/运行前拦截 |
| resource_exhausted | 可重试，建议延迟 |

### 3.5 外部生态接入（社区 Skill 包与 MCP，W-14）

**定案：外部能力不新增第四层、不绕过 SkillRuntime**——一切外部生态（社区 SKILL.md 渐进式包、MCP server tools）一律经适配器包装为 Skill 进入统一注册表，观测/权限/幂等/编排能力免费获得。`skill_type` 全枚举一步定义（W-15，§3.1）。

| 外部形态 | 适配方式 | 命名空间 |
|---|---|---|
| 社区 SKILL.md 包（frontmatter + 指令正文 + scripts/ + references/） | **Skill Hub 加载器拆解注册**：指令正文 → `prompt` Skill（invoke 时注入 ai_agent 上下文，渐进式披露 = 模型按需读）；scripts/ 脚本 → `script` 沙箱 Skill（bash/python/node 等，共享批次 3 沙箱）；references/ → 知识资产（注入 RAG/Agent 上下文，不单独成 Skill） | `pack.{包名}` |
| MCP server tools | **MCP adapter 反射注册**：连接时读取 tools 清单，JSON Schema → input_schema，实现 = MCP client 调用；幂等声明 `none`（MCP 无幂等语义）、execution 默认 inline | `mcp.{server}` |

约定：

- 拆解/反射产物统一标 `origin: external`（记录来源包/MCP server 与版本），与内置 Skill 同表同治（CA-01~CA-12 全部适用）；
- MCP resources/prompts 不直接暴露：resources 归知识资产管理，prompts 可按需包装为 `prompt` Skill；
- 加载器只做**声明翻译**不做语义改写——外部包治理（沙箱逃逸、副作用声明）仍按 §3.1 校验规则与批次 3 沙箱测试把关。

## 4. 执行体系：三条入口 → 一个运行时

### 4.1 三条平行入口（对应需求原文的三种触发方式）

```text
① Web Controller ────────┐   页面手动触发：知识库管理页点「解析入库」
② Agent Tool Adapter ────┼─▶ SkillRuntime.invoke() ─▶ Skill Impl ─▶ Service ─▶ Model/DAO
③ Task Executor ─────────┘   Celery worker 领取 task 后回调 SkillRuntime
```

| 入口 | 职责 | 不允许 |
|---|---|---|
| Web Controller | HTTP 参数、鉴权、SSE、调试台（`ai_skill:invoke` 权限，仅管理员/调试台） | 不复制调用逻辑、不感知 inline/queued 细节 |
| Agent Tool Adapter | 把 Skill 契约转成 LLM tool schema，路由到 SkillRuntime；对话附件自动匹配 Agent | Agent 不直接调用 Service |
| Task Executor（Celery） | 领取、超时、取消、回写进度，然后回调 SkillRuntime | 不实现业务 |

三条入口殊途同归——**这就是「问答自动入库、页面手动触发、推到 Celery」共享同一份实现与同一套观测的机制保证**。

### 4.2 inline vs queued（由 SkillRuntime 决定）

```text
1. Skill 声明 modes 只含 inline → inline（硬超时默认 ≤60s，轻量操作）
2. 只含 queued → queued（必须支持进度/取消）
3. 两者皆支持：输入规模超阈值 → queued；priority_class=batch → queued；否则 inline
4. inline 超时不自动转 queued（避免重复副作用），返回可重试错误并建议 queued
```

### 4.3 队列拓扑（最终设计，机制一步到位）

沿用 module_task 双引擎（local / celery）与 `task_queue` 表（先落库再投递，CA-10），在其上定义**物理隔离的最终拓扑**——priority_class / resource_domain 从第一天起就是真实调度机制，不存在「仅元数据」的过渡态（W-4）：

| 物理队列 | 承载 | worker 池 | 语义 |
|---|---|---|---|
| `q_interactive` | 会话链路内触发的 queued 调用（附件解析、会话内工具） | 独立小池（并发 = min(8, CPU/2)） | 延迟优先；软超时 + 超时降级回答 |
| `q_agent_job` | agent job（kb_ingest 等 fan_out 批处理） | 独立池（按 resource_domain 限流） | 吞吐优先；进度/断点续跑 |
| `q_task`（既有） | 存量任务类型 | 既有 worker | 不迁移存量，避免破坏性变更 |

- `priority_class`（interactive/standard/batch）：同队列内投递排序；**真实隔离靠物理队列**，不依赖 Celery 优先级（无抢占）。
- `resource_domain`（parse / index / llm / none）：任务注册表白名单，Skill 不能自造队列；每域配**准入配额**（如 parse ≤ MinerU 并发额度、index ≤ Milvus 写压、llm ≤ embeddings API 限速），由 Task Executor 领取时做信号量准入，超配额的 pending 留守 `task_queue`——形成**全局背压**。
- 防饥饿：q_interactive 独立池天然免疫批量拖累；q_agent_job 内 batch 类按 `scheduled_at` 公平轮转。

### 4.4 会话附件链路（问答时自动入库，需求原文场景）

1. 用户在对话中上传文件 → 服务端判定为 interactive，落 `task_queue` 投队列，带 soft deadline；
2. 问答 Agent（ai_agent）的工具清单**直接暴露 `doc_parse` 与 `doc_chunk_index` 两个 Skill 句柄**（Agent 调用 Agent 被禁止，CA-02）；模型匹配「用户希望基于该文件回答」意图后按 parse → index 顺序两次调用；长耗时首次调用返回 `{invocation_id, status: pending}` 句柄，模型在后续轮次以句柄续查（§2.4）；
3. 超时未完成 → 先回答已就绪内容并提示「文件仍在解析」；解析完成推事件，下一轮自动可引用；
4. 会话附件默认临时（TTL 清理），显式「存入知识库」才入库，且需项目写权限。

### 4.5 幂等 / 重试 / 取消 / 进度

- 幂等键由 Manifest `idempotency.keys` 生成，重复调用直接复用已有 invocation；
- 重试按 error_class（§3.4）；取消 = 任务取消 + 业务检查点；进度必须上报（queued 前提）。

## 5. 现有功能的三层化改造（首个样板）

### 5.1 `doc_parse` Skill（源自 module_office）

- 实现：包装既有 `ParserFactory`（MinerU remote/local，可扩展其他解析服务）；
- **双产物契约**：`markdown`（整篇）+ `blocks`（结构小块：层级/页码/表格定位）——两种输出正是当前解析器已有能力，只需在 Skill 契约中显式化；
- nature=hybrid：解析主干确定；`optional_capabilities=[ocr]`，OCR 缺失时跳过增强（核心文本缺失才失败，表格/图片增强允许降级且降级结果不得自动入库）；
- 保留既有「重新解析」语义为幂等重跑。

### 5.2 `doc_chunk_index` Skill（源自 module_rag）

- 实现：分块策略（规则 + 可选 chat 识别）+ 向量化 + 入库（Milvus/LanceDB）+ 引用记录；
- nature=hybrid：策略识别可选降级为默认策略（degraded=true）；
- **能力组（capability_alternatives，零依赖表态 W-6）**：`[[embeddings], [store: bm25]]`——向量完整路线（embeddings 必需）或 BM25-only 降级路线（仅 Milvus，零模型可跑，degraded=true）；LanceDB 纯向量模式无 BM25 组 → embeddings 严格必需，缺失即 `capability_missing`；
- 现有 `reparse_document_task` 拆解：Celery 体内不再直写三步逻辑，改为依次 `skill_runtime.invoke(doc_parse)` → `invoke(doc_chunk_index)`（首批过渡形态），随后由 `kb_ingest_agent` 接管。

### 5.3 `kb_ingest_agent`（static_agent，LangGraph 固定工作流）

- decision_mode=rule：`parse → index` 线性两步 + documents fan_out + collect 容错；
- 全程可零模型运行（ocr/策略识别均降级）；
- 同时是「知识库整库重建」「批量重向量化」的复用单元（不同入参/启用步骤）。

### 5.4 三条触发路径对照（需求概念例子 → 机制落点）

| 需求原文 | 机制 |

## 11. 评审定案与权衡记录（v1.1）

> 本章是 2026-11-11 设计评审的**最终决议存档**：A 类（内在矛盾）4 项采纳修正、B/C 类 8 项权衡定案，另含 2 项外部生态接入增补（W-14/W-15）。正文已按定案改写，此处记录「为什么这么定」，防止后续实施者重新引入已被否决的方案。编号 W-1~W-15 与正文引用一一对应。

### 11.1 定案表

| 编号 | 议题 | 定案（正文落点） | 否决的备选 | 定案理由 |
|---|---|---|---|---|
| W-1 | Agent 是否可调用 Agent | **禁止，且无过渡形态**（CA-02、§2.4、TL;DR #6） | ① 允许嵌套但禁递归；② 过渡期允许 job Agent 编排 | 对话场景 ai_agent 直接编排 Skill 句柄（§4.4）、批处理场景 static_agent steps 编排（§3.3），两种场景均无需嵌套即可表达；允许嵌套会把调度器演变成通用工作流引擎，状态空间与失败模式不可控 |
| W-2 | doc_parse 降级产物如何阻止自动入库 | **编排层批内条件 `skip_if`**（§3.3 steps 示例、§5.2） | ① Skill 内部静默丢弃；② doc_chunk_index 入参校验拒绝 | 「降级结果是否可用」是编排决策不是能力语义：同一 doc_parse 产物在「人工预览」场景可用、「自动入库」场景不可用，判定必须在编排层表达，Skill 保持纯粹 |
| W-3 | agent_job_run 是否后置 | **设计内建，批次 1 交付**（§6、§9 批次 1） | v1 先用 task_queue 聚合、v2 再补表 | Agent 级幂等键（同 job 重复提交去重）与步骤级断点续跑没有载体就是空话；后置意味着 v1 的 job 无幂等语义，迁移时口径断裂 |
| W-4 | 队列机制是否分 v1/v2 两套语义 | **不分，一步到位**（§4.3 最终拓扑、§9「分期只是交付顺序」） | v1 priority_class 仅元数据、v2 再生效 | 语义欠债必然误导实施者：v1 若不实现准入排序，上线后交互任务与批量同池竞争的问题立即复现，等 v2 改造时要迁移存量语义。分期只切交付内容（批次 2 才物理拆池），不切机制语义 |
| W-5 | static_func 放 Model 层还是独立第四层 | **维持供给层定位 + 契约显式分叉**（§2.2 分叉表） | ① 独立 Function 第四层；② 下沉为 static_skill | 它与 ai_model 同为「被绑定的供给品」（Skill 声明能力、运行时解析到 LLM 或规则函数，实现无感），抽出去会多一层几乎同构的注册/解析/绑定机制；风险用契约分叉（超时/失败模式/成本/缓存语义逐项不同）+ 双源合并一致性校验 + 纯函数约定压制 |
| W-6 | 「零依赖可运行」边界含糊 | **明确表态**：零依赖 = 平台可启动 + static 能力链路（static_func/static_skill/rule Agent）可运行 + `doc_chunk_index` 走 BM25-only 降级入库（仅 Milvus）可运行且 degraded=true；LanceDB 纯向量模式下 doc_chunk_index 的 embeddings **严格必需**，缺失即 `capability_missing`（§5.2 能力组） | 把「向量入库」也纳入零依赖承诺 | LanceDB 无 BM25 能力，纯向量检索没有 embeddings 就是空转；承诺超出存储引擎能力即是谎言。BM25-only 降级路线让 Milvus 用户零模型可用，LanceDB 用户得到诚实的快速失败 |
| W-7 | Skill 命名冲突与对话 tool 名约束 | **`{namespace}.{key}` 全局唯一**，namespace ∈ sys/usr（后续第三方扩展）；LLM tool-calling 名称中 `.` 映射为 `_` 传给模型、回查时还原（§3.1） | 允许跨 namespace 同名 | 内置与用户自定义必然争短名；tool-calling 主流协议对函数名字符集有限制，映射方案零成本解决且可逆 |
| W-8 | Skill 状态机是否三层统一 | **双生命周期**：内置 Skill 走代码生命周期（同步即 published、删除即下线、可标 deprecated 提示）；自定义 Skill 走 DB 状态机 draft→published→deprecated（§6 ai_skill 行） | 全部统一 DB 状态机 | 内置 Skill 由 git 管理版本，DB 状态机对它是冗余状态副本（改代码还要改状态才能生效，必然漂移）；自定义 Skill 无代码载体，必须有状态机 |
| W-9 | API 契约是否为 vue3 提供兼容过渡层 | **一步到位**：`/agent/skills` 直接返回 Manifest 视图，vue3 能力中心与 flutter 智能体页在同一交付内完成适配（§5.5、§7） | ① 先出旧视图兼容层再切换；② vue3 先适配、flutter 缓一版 | 基线项目两端（web/flutter）同仓同版本交付，过渡层没有存续期，只增加一次全链路回归成本 |
| W-10 | 对话中 Skill 失败如何反馈 | error_class 映射固定文案注入 ToolMessage，模型据此决定重试/换路/告知用户，不向用户裸抛异常（§3.4 失败语义） | 直接把异常栈透传给模型或用户 | 异常栈既不安全又超 token；固定文案保证三类 error_class 在模型侧行为可预期 |
| W-11 | 批处理完成如何通知前端 | ag-ui 协议**新增 `task_done` 事件**（§4.4） | 复用现有 error/end 事件夹带 | 完成通知是独立语义（含 job_run_id/聚合结果摘要），夹带在既有事件里会让客户端解析逻辑分叉；ag-ui 自定义事件是官方预留的扩展点 |
| W-12 | static_agent 与 ai_agent 运行时是否统一 | 同用 LangGraph `StateGraph` + PostgreSQL checkpointer：static_agent 只是分支全部显式（无模型节点）的图，断点续跑/状态持久机制完全复用（§2.4 状态行） | 为 static_agent 单独写步骤执行器 | 一套图运行时两种形态免费共享 checkpointer/重放/观测；单独执行器是第二套要维护的状态机 |
| W-13 | skills/ 目录放哪 | **模块第八类目录**：`module_rag/skills/`、`module_office/skills/` 等与 controller/service/dao 平级，Skill 归属其领域宿主模块（§5.6）；落地时修订后端 README_AI 的模块结构清单 | ① 全部集中到 module_agent/skills/；② 顶层 skills/ | 集中目录会让领域模块反向依赖 agent 模块（Skill 实现要调本模块 Service）；Skill 是宿主模块的对外资产，与 Service 平级符合「实现薄包装」原则 |
| W-14 | 外部生态（社区 SKILL.md 包、MCP tools）如何接入 | **不新增第四层、不绕过 SkillRuntime**（§3.5）：SKILL.md 包由 Skill Hub 加载器拆解（指令→prompt Skill、脚本→script 沙箱 Skill、references→知识资产）；MCP tools 由 adapter 反射注册（JSON Schema→input_schema，实现=MCP client 调用） | ① 为渐进式包新设「Asset 资产层」；② MCP tools 直接暴露给模型、绕过运行时 | 外部能力一旦绕过 SkillRuntime，观测/权限/幂等/配额全部失守；包装为 Skill 后与内置能力同权同治，CA-01~CA-12 免费获得。渐进式披露本质是「模型按需读指令」，与 SkillRuntime 调用不冲突，拆开注册即可两全 |
| W-15 | skill_type 枚举是否只做首批 | **一步定义全**：`builtin_tool / prompt / python_script / script / mcp_tool`（§3.1），`script` 为 python_script 的语言泛化（共享同一沙箱）；交付节奏仍按批次（批次 2 prompt、批次 3 其余），契约定义与交付节奏解耦 | 首批只留 builtin_tool、后续批次再补枚举 | 枚举是契约不是实现：全量先定死可防止批次间命名漂移（如先叫 python_tool 后改 script）；「分期只是交付顺序不是语义分期」同样适用于类型枚举 |
