# 06 - AI 智能体场景设计（场景化组合 · 产物交付 · 运营收口）

> **文档定位**：REQ-002。在 [04-AI能力平台架构设计](./04-AI能力平台架构设计.md) 的三层契约与 [05-对话智能体与执行协议设计](./05-对话智能体与执行协议设计.md) 的执行协议之上，把「能力」变成「场景」：交付三个开箱即用的内置场景 Agent（深度研究、批量文档、办公创作），抽出统一的**场景底座**（产物归档 / 验收模板 / 场景入口），并收口 REQ-019 遗留的平台小项（`agent.*` 事件前端消费与任务清单视图、北极星看板、human 验收闭环）。
>
> **权威边界**：三层契约以 04 为准；执行协议（五拍协议、验收闸门、模式解析、Skill 自动调用）以 05 为准。本文**不新增执行机制**，只做场景装配、底座补齐与观测收口；冲突时以 04/05 为准。
>
> 版本：v1.0（2026-11-17 首版，配套 REQ-002）

---

## 0. 结论摘要（TL;DR）

1. **场景 = Manifest + Skill 组合 + 验收模板 + 前端入口**，不引入任何新的执行范式。三个场景 Agent 全部是代码 Manifest 内置（同 05 §2.1 的双生命周期原则），管理员只读可见、可 `config_override`。
2. **策略按任务性质选**：研究与批处理是「多步交付、可自动验收」→ `plan_execute`（五拍协议）；办公创作是「单文件对话式生成」→ `react`（有界 ReAct，无清单，用自动结构校验替代验收闸门）。
3. **产物必须落虚拟文件系统**：当前 plan_execute 的 workspace 是 `tempfile.mkdtemp`，验收完即丢，用户拿不到文件。批次 7 增加**产物归档**：verdict 通过后上传 VFS `/agent_runs/{run_id}/`，`agent_plan_item.artifact_files` 记 `file_id`，前端 verdict 卡片可直接预览/下载（复用 REQ-016）。
4. **验收模板是建议，不是第二套语义**：模板只作为 `write_plan` 时的候选清单注入；`acceptance_hash` 防削弱机制原样生效，模型可加强不可减弱。
5. **平台收口先于场景**（批次 6）：`agent.plan_update` / `agent.verdict` / `agent.skill_masked` 前端消费 + 会话内任务清单折叠块 + 北极星看板。理由：场景的可信度建立在前端能看到「计划—验收—产物」这条链上，看不见就无法评审。
6. **北极星看板只做三项 + 两项下钻**：假完成率 / 任务成功率 / 每成功任务成本；下钻看首次交卷通过率与预算触顶率。不建通用 BI。
7. **human 闭环用「挂起—续跑」**，不在进程内阻塞等待审批；超时默认未通过并进入两败改单。该项为 P2 可选批次。
8. **明确不做**：Agent 调 Agent、Agent 市场、MCP SSE 传输、Skill 热更新、多租户配额与结算（沿用 04 §11.2 后置边界）。

## 1. 差距盘点与场景选型

### 1.1 现状（2026-11 基线）

| 现状 | 位置 | 缺口 |
|---|---|---|
| 平台有完整执行协议，但无面向终端用户的场景 Agent | `module_agent/agents/`（builtin/kb_ingest/ops） | 用户不知道「能拿它做什么」；每次都从空会话开始 |
| plan_execute 产物落在临时目录 | [runner.py](../../code/backend/server_py/src/module_agent/service/runner.py#L251-L252) | 验收通过即丢失，**不可交付** |
| `agent.plan_update` / `agent.verdict` 后端已下发 | `module_ai/utils/llm/stream/agui.py` | [agui.ts](../../code/frontend/vue3/src/common/types/agui.ts#L66-L75) 只认 4 个 CUSTOM 事件，无清单视图 |
| `skill_masked` 只汇成文本摘要 | `module_rag/utils/llm/stream_classifier.py` | 没有结构化 `agent.skill_masked` 事件 |
| 北极星三项数据已落库，无聚合 | `agent_plan_item` / `skill_invocation` | 无看板；`usage` 只在内存，未落事件 |
| human 验收只有回调签名 | `agent_planner.py`（`human_fn`） | 无挂起/通知/审批入口/超时策略 |
| Skill 资产齐备但未被场景化 | `builtin/`(4)、`module_office/doc_parse`、`module_rag/doc_chunk_index`、`module_task/container_ops`、Skill Hub(docx/pptx/xlsx) | 缺少「场景 → 技能」的固定组合与前置条件提示 |

### 1.2 场景选型（为什么是这三个）

| 候选场景 | 判定 | 理由 |
|---|---|---|
| **深度研究**（`research_agent`） | ✅ 首批 | 与已有能力最贴合（检索 + 联网 + Rerank）；交付物是报告，**验收可全自动**（章节/引用/字数）；最能体现五拍协议价值 |
| **批量文档处理**（`batch_docs_agent`） | ✅ 首批 | 会话多附件 + doc_parse + 社区 docx/pptx/xlsx 包，逐文档一项、天然可验收；企业高频 |
| **办公创作**（`office_agent`） | ✅ 首批 | 「一句话生成 docx/xlsx/pptx」是用户对 AI 最直观的期待；单文件创作不需要清单，正好验证 react 场景下的轻量校验路径 |
| 运维自愈 | ❌ 不做 | REQ-019 已交付 `ops_agent`，再做即重复 |
| 代码助手 / SQL 分析 / 数据分析 | ⏸ 后置 | 需要沙箱与数据集管理，成本高、验收标准难统一 |
| 万能 Agent（一个 Agent 全场景） | ❌ 否决 | 场景提示词互相稀释，工具集臃肿，验收标准无法固定 |

**边界**：场景 Agent 是**内置只读 Manifest**，用户不可编辑其提示词与验收模板（可复制为自定义 Agent 再改，走既有能力）。

## 2. 场景底座（三件套）

三个场景共用同一套底座，避免每个场景各写一套。

### 2.1 产物 VFS 归档

```text
plan_execute / react 运行
   → workspace(tempfile) 产出 orchestrator.md / report.md / out.docx
   → verdict.passed(或 react 结构校验通过)
   → ArtifactArchiver.archive(run_id, artifacts, user_id, conversation_id)
        ├─ FileService.ensure_module_root("agent_run", "智能体产物")
        ├─ ensure_folder(run_id)                      # /智能体产物/{run_id}/
        ├─ upload_content_bytes(内容) + create_entry  # 落虚拟文件树
        └─ 返回 [{file_id, name, size, mime}]
   → agent_plan_item.artifact_files 回填 + 事件 payload 附 files
```

硬规则：

| 规则 | 说明 |
|---|---|
| 只归档验收通过的产物 | 未通过项不归档，避免用户拿到半成品；重试覆盖同名文件 |
| 按 run 隔离目录 | `/智能体产物/{run_id}/`，run_id 与 `agent_plan_item.run_id` 同源，可直接反查 |
| 幂等 | 归档键 = `run_id + 文件名`；重复归档走覆盖更新，不产生重复条目 |
| 大小与类型 | 单文件超 `max_size_bytes` 走分片上传；MIME 由扩展名推断（同 `_guess_mime`） |
| 权限 | 归属 `owner_user_id` = 会话用户；他人不可见（VFS 既有权限模型） |
| 失败不阻断 | 归档失败只记 warning 并在报告尾部提示「产物归档失败」，不影响 verdict 结论 |

> 归档是**运行结束后的旁路动作**，不进入验收链路：验收只认 workspace 内的文件（05 §4.4），归档是交付通道。

### 2.2 验收模板库

```python
# module_agent/service/acceptance_templates.py
TEMPLATES = {
    "research_report": [
        Acceptance("artifact", "report.md: ##>=4, [>=8, 字数>=1200"),
    ],
    "doc_transform": [
        Acceptance("artifact", "{output}: 空文件检查"),
        Acceptance("cmd", "test -s {output}"),          # 非空
    ],
    "office_file": [
        Acceptance("artifact", "{output}: 存在"),
    ],
}
```

规则：

- 模板只用于 `write_plan` 提示：执行器把可用模板清单（名称 + 一行 render）放进技能目录区，模型自行选用；
- **模板不自动生效**：模型必须在 `write_plan` 中显式写入 `acceptance_kind/spec`，落库后即固化；
- `acceptance_hash` 防削弱机制不改：模板变更不会让已有 run 的验收放宽；
- 模板不引入新 `kind`，仍是 05 §4.4 的 `cmd / artifact / judge / human`。

> artifact spec 语法沿用现状：`文件路径: 关键词>=N`（见 [acceptance.py](../../code/backend/server_py/src/module_agent/service/acceptance.py#L171-L252)）。「字数」用 `关键词>=N` 表达受限，批次 7 为 `_parse_artifact_spec` 增加 `chars>=N` / `lines>=N` 两个确定性谓词（只加谓词，不动语义）。

### 2.3 场景入口

| 端 | 入口 | 行为 |
|---|---|---|
| flutter 客户端 | 新对话空态功能卡片（既有「后续新功能默认入口」约定） | 三张卡片：深度研究 / 批量文档 / 办公创作；点击 = 新建会话并绑定对应 `agent_id` |
| vue3 toC（`modules/chat`） | 输入区上方的「场景」快捷选择（与既有模式选择器同一行） | 同上；当前 Agent 名常驻显示 |
| vue3 toB（`modules/agent`） | 智能体页「内置场景 Agent」只读区 | 展示 Manifest（策略 / 技能 / 验收模板 / 预算），可「复制为自定义」 |

- 入口只传 `agent_id`，不传任何执行参数——策略与预算由 Manifest 决定，前端不参与；
- 未交付场景（如批次 8 前）卡片置灰并提示「即将上线」，不隐藏，便于用户形成预期。

## 3. 场景一：深度研究 Agent（`research_agent`）

### 3.1 Manifest

```yaml
key: research_agent
name: 深度研究
agent_kind: chat
decision_mode: model
execution_strategy: plan_execute
description: 给定研究主题, 产出带编号引用的研究报告(report.md)
skills: []                       # 走 §5.1 条件注册
chat_modes:
  plan_execute:                  # 预算覆盖(runner 已支持 chat_modes["plan_execute"])
    max_model_calls: 40
    max_tool_calls: 60
    wall_clock_s: 900
system_prompt: |
  你是研究分析助手。把研究主题拆成「检索—取证—成文—自校」的清单,
  每一项的验收必须客观可查; 报告必须逐条标注来源编号, 不得出现无出处结论。
```

### 3.2 Skill 组合与前置条件

| Skill | 注册条件 | 在场景中的角色 |
|---|---|---|
| `web_search` | 用户开启联网搜索 | 外部事实取证 |
| `kb_search` | 会话命中知识库且用户有检索权限 | 内部资料取证 |
| `file_search` | 会话有附件（复用 04 会话附件链路） | 附件内容取证 |
| Skill 句柄 | `agent_callable=true` 且已发布 | 模型自选（如 run_script 做统计） |

**前置提示**：无联网且无知识库且无附件时，不启动 run，直接返回「请先开启联网或选择知识库」，避免空烧预算（05 §4.6 守卫的语义前置）。

### 3.3 清单样例与验收

模型典型 `write_plan`（示意，非硬编码）：

| id | goal | acceptance |
|---|---|---|
| s1 | 明确研究范围与关键问题 | `judge: 至少 3 个可检索的子问题` |
| s2 | 检索并整理证据 | `artifact: evidence.md: 来源>=5`（每条含标题与链接） |
| s3 | 撰写报告 | `artifact: report.md: ##>=4, [>=8, chars>=1200` |
| s4 | 自校引用与结论一致性 | `judge: 每个结论都有来源编号; 无编号结论=0` |

要点：

- `s4` 的 judge 是**干净上下文**判官（05 §4.4 规则 3），只见 goal / 验收 / 产物；
- 引用编号在 `report.md` 中形如 `[1]`，末尾附「来源列表」，`[>=8` 的计数即引用数；
- 字数谓词用 `chars>=1200`（批次 7 新增谓词），不用字符关键词硬凑。

### 3.4 交付形态

- 归档产物：`report.md`（主交付）+ `evidence.md`（取证记录）；
- 最终报告文本（`ANSWER` 流）保持「逐项 ✓/✗ + 尝试次数」的既有格式，末尾追加产物文件清单；
- 前端 verdict 卡片与最终报告均可点开 `report.md` 预览（REQ-016 预览能力）。

## 4. 场景二：批量文档处理 Agent（`batch_docs_agent`）

### 4.1 Manifest

```yaml
key: batch_docs_agent
name: 批量文档处理
execution_strategy: plan_execute
chat_modes:
  plan_execute:
    max_model_calls: 60
    max_tool_calls: 120
    wall_clock_s: 1800
system_prompt: |
  你要处理会话中的全部附件。每个附件一项清单, 逐项产出结果并交卷;
  转换类产物必须可被再次打开(非空、结构完整), 汇总类产物必须列出全部文件名。
```

### 4.2 Skill 组合

| Skill | 注册条件 | 角色 |
|---|---|---|
| `doc_parse` | 会话有可解析附件 | 附件 → markdown + 结构块 |
| `pack.docx` / `pack.pptx` / `pack.xlsx` | Skill Hub 已加载对应社区包 | 格式转换 / 生成 |
| `run_script` | 沙箱已启用且配置完整 | 批内聚合、文件打包 |
| `kb_search` | 命中知识库 | 可选补充上下文 |

### 4.3 任务组织

- **一项一文档**：清单项 id = `doc_{序号}`，goal 含文件名，便于用户对照；
- **fan-out 不引入**：五拍协议清单是线性的，逐项串行执行（并发由 `run_script` 内部处理）；理由见 W-23；
- **汇总项收尾**：最后一个清单项 = 「生成处理汇总」（`artifact: manifest.md: 文件数>=N`），N 为附件数，防止漏处理；
- **失败隔离**：单个文档两败后改单（拆分/换解析器/标注无法处理），不阻塞其余文档；最终报告逐项标注。

### 4.4 交付形态

- 归档：每个转换产物 + `manifest.md`（处理清单：文件名 → 状态 → 产物名）；
- 超 10 个产物时，额外用 `run_script` 打 zip 一并归档；
- 前端最终报告展示「✓/✗ 文件名」分组，点击跳 VFS。

## 5. 场景三：办公创作 Agent（`office_agent`）

### 5.1 为什么是 react 而不是 plan_execute

单文件创作（「把这段会议纪要整理成一页 PPT」）是**对话式单步交付**：没有多步依赖、没有长任务漂移风险，上五拍清单只会增加延迟与 token。因此：

- `execution_strategy=react`（有界 ReAct，05 §3）；
- 用 **自动结构校验** 替代验收闸门：产物生成后由运行时做确定性检查（文件存在、非空、可被对应库打开、页数/行数下限），失败则把原因作为 `ToolMessage` 回灌让模型重试一次；
- 不写 `agent_plan_item`（无清单），但**仍归档产物**并下发 `agent.artifact_ready` 事件（新增，见 §6.1）。

### 5.2 Manifest

```yaml
key: office_agent
name: 办公创作
execution_strategy: react
chat_modes:
  thinking: { think_level: low, max_loops: 4, max_model_calls: 6, max_tool_calls: 8, wall_clock_s: 120 }
  deep:     { think_level: high, max_loops: 6, max_model_calls: 8, max_tool_calls: 12, wall_clock_s: 180 }
system_prompt: |
  你把用户的描述转成可直接使用的办公文件(docx/pptx/xlsx)。
  先确认目标格式与结构要点, 再调用对应技能生成; 生成后自检是否满足结构要求。
```

### 5.3 结构校验规则

| 产物类型 | 确定性校验 | 失败处理 |
|---|---|---|
| `.docx` | 存在、非空、`python-docx` 可打开、段落数 ≥ 3 | 原因回灌，模型重试 1 次；再失败则明确告知 |
| `.pptx` | 存在、非空、可打开、页数 ≥ `req.pages or 3` | 同上 |
| `.xlsx` | 存在、非空、可打开、至少 1 个非空 sheet | 同上 |

> 校验阈值可由用户在话术中点明（如「做 8 页」），运行时从工具入参读取 `pages/sheets`，不猜。

### 5.4 交付形态

- 归档到 `/智能体产物/{run_id}/`；run_id 由 react 分支生成（与对话消息绑定）；
- 下发 `agent.artifact_ready`（`{files:[{file_id,name}], source:"office_agent"}`），前端消息内出现「文件卡片」；
- 不产生清单块，避免用户误以为有任务在执行。

## 6. 前端协议消费（FEAT-AGENT-008，批次 6）

### 6.1 事件契约（后端 → 前端）

| CUSTOM 名 | 触发 | value 结构 | 现状 |
|---|---|---|---|
| `rag.mode_decision` | 模式解析完成 | `{requested_mode, exec_mode, reason}` | ✅ 已消费 |
| `agent.plan_update` | `write_plan` / `revise` | `{event_type, message, plan_count, items:[{id,goal,acceptance,status,attempts,last_reason}]}` | ⚠️ 后端已发，前端未消费 |
| `agent.verdict` | 每次验收 | `{event_type, message, item_id, passed, reason}` | ⚠️ 同上 |
| `agent.skill_masked` | 会话内技能熔断 | `{skill_key, reason, message}` | ❌ **仅文本摘要，需补结构化下发** |
| `agent.artifact_ready` | 产物归档完成 | `{files:[{file_id,name,size,mime}], source}` | ❌ 新增 |

后端改动（仅两处）：

1. `stream_classifier` 将 `deep_events` 中 `type=skill_masked` 的项转成带 `data.event_type="agent.skill_masked"` 的 `tool_call` 流（走 agui 既有 `agent.*` 透传分支），不再只折叠为文本；
2. `runner` 在归档成功后下发 `agent.artifact_ready`。

### 6.2 前端消费

`common/types/agui.ts`：

```ts
export const AGUI_CUSTOM_NAME = {
  STATUS: 'rag.status',
  INTENT_RESULT: 'rag.intent_result',
  INTERACTION: 'rag.interaction',
  MODE_DECISION: 'rag.mode_decision',
  PLAN_UPDATE: 'agent.plan_update',
  VERDICT: 'agent.verdict',
  SKILL_MASKED: 'agent.skill_masked',
  ARTIFACT_READY: 'agent.artifact_ready',
} as const
```

`useAguiMessages.ts` 新增两类聚合：

- **清单块（单例）**：`plan_update` 全量替换 `planItems`；`verdict` 按 `item_id` 就地更新 `status/attempts/reason`。清单块**不追加**，始终只有一个（与 `appendBlock` 的合并语义不同，需独立字段 `plan: PlanItem[] | null`）；
- **产物块**：`artifact_ready` 追加 `kind='artifact'` 块，渲染文件卡片（名称/大小/预览/下载）。

渲染规范：

| 状态 | 图标 | 文案 |
|---|---|---|
| pending（当前项） | ◐ | 「进行中」 |
| pending（后续项） | ○ | 灰显标题一行 |
| done | ✓ | 标题 + 「已验收」 |
| 未通过 | ✗ | 标题 + `reason`（一行截断，可展开） |

### 6.3 断线兜底与历史回放

- 流中断线：收到 `RUN_ERROR` 或网络断开后，若已知 `run_id`（从 `plan_update` 事件取得），调 `GET /agent/plans/{run_id}` 补全清单终态；
- 历史会话：消息 `process_blocks` 已持久化过程块，重开会话直接渲染；清单块若在 blocks 中无终态，按 `run_id` 拉一次投影覆盖；
- 两者以「投影优先」：实时态与投影不一致时以 `agent_plan_item` 投影为准（05 §4.8 单向投影原则）。

## 7. 北极星看板（FEAT-AGENT-009，批次 6）

### 7.1 指标口径

| 指标 | 公式 | 数据源 |
|---|---|---|
| 假完成率 | `done 且 verdict_passed≠true` / `done`（**不变量监控，正常恒为 0**） | `agent_plan_item` |
| 任务成功率 | `stop_reason=completed` 的 run 数 / 总 run 数 | `agent_plan_event(run_finished)` |
| 每成功任务成本 | 成功 run 的平均 `(input_tokens+output_tokens, tool_calls, elapsed_ms)` | `agent_plan_event(run_finished)` |
| ⇩ 首次交卷通过率 | 首次 submit 即通过的项数 / 总项数 | `agent_plan_item.attempts=1 & verdict_passed` |
| ⇩ 预算触顶率 | `mode_budget_hit=true` 的 run 数 / 总 run 数 | `skill_invocation` / event |

**必要补齐**：`usage` 当前只在内存（`PlanRunResult.usage`），不落库。批次 6 在 run 结束时写一条 `run_finished` 事件，payload = `{stop_reason, status, usage, item_total, item_passed, revisions}`。这是看板的唯一新增依赖。

### 7.2 端点

`GET /agent/metrics/north-star?start=&end=&agent_key=`（管理员）

```json
{
  "fake_done_rate": 0.0,
  "success_rate": 0.72,
  "cost_per_success": {"tokens": 18234, "tool_calls": 11.4, "elapsed_ms": 96200},
  "drilldown": {"first_submit_pass_rate": 0.61, "budget_hit_rate": 0.08},
  "runs": 125,
  "window": {"start": "...", "end": "..."}

```

- 只读聚合，不落物化表（数据量在万级以内，直接 SQL 聚合）；

### 7.3 页面

`modules/agent` 新增「运行看板」页签：三张指标卡 + 一张按天的趋势折线 + 失败 run 列表（可跳 `GET /agent/plans/{run_id}/events` 回放）。

## 8. human 验收闭环（FEAT-AGENT-014，批次 8 · 可选）

### 8.1 挂起—续跑（不阻塞进程）

```text
verify(item, ...)  kind=human
  → 落 agent_plan_event(human_requested, {approval_id, item_id, summary})
  → agent_plan_item.status = awaiting_human      （新增状态，仅 human 项使用）
  → run 以 stop_reason="awaiting_human" 优雅收尾（进程释放）
  → 通知中心站内信 + 会话内审批卡片 + toB 审批入口
  → 批准: POST /agent/plans/{run_id}/approve → 触发续跑（已完成项跳过, 从挂起项继续）
  → 拒绝/超时(默认 24h): 视为未通过 → attempts+1 → 两败改单
```

要点：

- **续跑是新建一次 run**（新 run_id，`parent_run_id` 指向原 run），避免长驻进程与 checkpointer 迁移复杂度；
- 已完成项从 `agent_plan_item` 投影恢复，不重复执行；
- 超时策略由 `human` 验收 spec 携带（`human: timeout=24h`），默认 24h；
- 审批人 = 会话用户本人；toB 侧管理员可代批（沿用既有权限）。

### 8.2 新增事件与端点

| 类型 | 名称 | 说明 |
|---|---|---|
| CUSTOM 事件 | `agent.human_review` | `{run_id, item_id, approval_id, summary, expires_at}` |
| 端点 | `POST /agent/plans/{run_id}/approve` | body `{approval_id, approved, comment}`，本人或管理员 |
| 端点 | `GET /agent/approvals/pending` | toB 批处理列表 |

## 12. 评审定案与权衡记录（v1.0）

| 编号 | 议题 | 定案 | 否决的备选 | 理由 |
|---|---|---|---|---|
| W-21 | 场景如何落地 | **内置场景 Agent（Manifest + Skill 组合 + 验收模板 + 入口）**，不新增执行机制 | ① 万能 Agent；② 每个场景写独立服务 | 万能 Agent 提示词互相稀释、验收无法固定；独立服务重复实现五拍协议 |
| W-22 | 产物如何交付 | **归档到 VFS `/智能体产物/{run_id}/`**，验收只认 workspace | ① 直接下载临时文件；② 存对象存储不纳管 | 临时文件验收完即丢；绕过 VFS 即失去权限、预览与统一管理 |
| W-23 | 批处理是否并发 | **串行逐项**，并发交给 `run_script` 内部 | 清单 DAG + fan-out | 05 §4.10 明确「任务真并行且共享资源」才升 DAG；当前无共享资源信号 |
| W-24 | 办公创作是否上五拍 | **不上，走 react + 自动结构校验** | 统一全部 plan_execute | 单文件创作无多步依赖，上清单只增加延迟；但必须有确定性校验兜底 |
| W-25 | 验收模板的效力 | **建议性候选，不自动生效** | 强制模板 / 模板可削弱 | 强制会剥夺模型合理分解空间；可削弱破坏 `acceptance_hash` 不变量 |
| W-26 | 看板范围 | **三项北极星 + 两项下钻** | 通用 BI / 全指标面板 | 05 §4.9 明确其余指标只在北极星恶化时下钻，面板会引导错误关注 |
| W-27 | human 审批实现 | **挂起—续跑（新 run + parent_run_id）** | 进程内等待 / 定时轮询 | 进程内等待占用 worker 且无法跨重启；轮询浪费且延迟高 |
