## 0. 结论摘要（TL;DR）

1. **模式即 Agent**：问答的 `fast` / `thinking` 不再是散落在函数签名里的布尔开关，而是两个**代码 Manifest 内置对话 Agent**（`builtin_fast` / `builtin_thinking`），模式配置 `chat_modes` 挂在 Agent 上；`deep` 是 thinking Agent 内部的**升级执行模式**，不是第三个 Agent。
2. **两级模式**：`requested_mode`（用户选择：auto/fast/thinking）→ `exec_mode`（执行模式：fast/thinking/deep）。解析器输入 = 请求模式 + 意图信号 + 工具可用性，输出 = 执行模式 + 决策理由（前端可见）。
3. **ReAct 必须有界**：通用执行器 `AgentRunner`（业务无关）守四重预算（轮次 / 模型调用 / 工具调用 / 墙钟），并做**分步思考档位切换**（规划 high、结果回填 off）；业务侧只负责构建工具与收集证据，**回答在循环外**产出。
4. **五拍协议**：任务型 `ai_agent`（`execution_strategy=plan_execute`）按「一条清单、一个循环、一道闸门」执行——模型只做分解、执行、交卷、按失败原因改单；**完成由验收判定，模型没有「完成」按钮**；失败两次必须改单；上下文严格一屏。
5. **不用通用 TodoList**：采用「清单 = 任务对象」的唯一数据模型（`Item`/`Acceptance`/`Submission`/`Verdict`），`write_plan` / `submit` 是**运行时控制动词**（不是 Skill、不进业务注册表），避免通用 todo 插件「不驱动循环、模型易忘计划」的问题。
6. **不用 langgraph prebuilt**：`create_react_agent` / `TodoListMiddleware` 一律不采用——预算、思考档位、证据分离、Skill 熔断、验收闸门都需要定制实现；LangGraph 只保留其擅长部分（编排图 + checkpointer + interrupt），与 04 的 W-12 结论一致。
7. **Skill / 知识库自动调用**：tool-calling 清单由 Skill 注册表**按能力条件生成**（无知识库不注册检索工具、未开联网不注册联网工具）；执行模式随意图信号自动升级（fast → thinking → deep）；所有自动调用严格受 `project_ids` / `user_id` 注入约束（CA-08）。
8. **运维能力 Agent 化**：docker 原语收编为 `sys.container_*` 系列 static_skill，伸缩 / 自愈编排收编为 `ops_agent`（static_agent，rule 决策）；`app_agent.py`（现更名 `app_host_probe.py`）降级为**同镜像第二入口的探针进程**，不再是架构外的孤本。
9. **交付批次**：批次 4 = 模式即 Agent + 有界 ReAct + 自动调用强化 + 运维 Agent 化；批次 5 = 五拍协议（plan_execute / 验收闸门 / 一屏上下文 / 一行经验）。

## 2. 模式即 Agent：内置对话 Agent 与模式策略

### 2.1 内置对话 Agent（代码 Manifest 为唯一事实源）

内置 Agent 由代码 Manifest 声明并只读同步进 `ai_agent` 表（同 Skill 的双生命周期原则，04 §6 W-8）；管理员的调整落在 `config_override`，不改代码。

```yaml
# module_agent/agents/builtin.py
key: builtin_fast
name: 快速问答
agent_kind: chat
decision_mode: model
execution_strategy: direct          # direct | react | plan_execute
chat_modes:                         # 模式策略配置（04 的三层契约在此扩展）
  fast:
    think_level: off               # 思考档位：off | low | high
    search_rounds: 1               # 检索轮次
    max_loops: 2                   # ReAct 轮次上限
    max_model_calls: 3
    max_tool_calls: 4
    wall_clock_s: 30
  deep:                             # thinking Agent 内部升级档
    think_level: high
    search_rounds: 3
    max_loops: 6
    max_model_calls: 8
    max_tool_calls: 12
    wall_clock_s: 90
skills: []                          # 走条件注册（§5.1），不在此静态列举
system_prompt: |

key: builtin_thinking
name: 深度问答
agent_kind: chat
decision_mode: model
execution_strategy: react
chat_modes:
  thinking:
    think_level: low
    search_rounds: 2
    max_loops: 4
    max_model_calls: 6
    max_tool_calls: 8
    wall_clock_s: 60
  deep:
    think_level: high
    search_rounds: 3
    max_loops: 6
    max_model_calls: 8
    max_tool_calls: 12
    wall_clock_s: 90
```

规则：

- `builtin_fast` / `builtin_thinking` 是**平台内置**，不可删除（删除即下线该模式入口）；用户可另建 chat Agent，但模式解析只认内置两者的 `chat_modes`（保证策略有唯一来源）。
- `deep` 档只在 thinking Agent 内定义（fast Agent 升到 deep 会失去「快」的语义，且预算翻倍），fast Agent 无 deep 档时升级请求直接落到 thinking 的 deep 档。
- 模式配置优先级：**内置 Agent `chat_modes` > 平台配置节 `ai_chat_modes` > 硬编码默认值**（三级回退，保证配置缺失不崩）。

### 2.2 两级模式解析

```text
输入：requested_mode(auto|fast|thinking) + 意图信号 + 工具可用性
      意图信号 = 复合问题 / 需要多源交叉 / 显式要求"深度思考" / 历史轮次回退意图
      工具可用性 = 是否有可用知识库、是否开启联网、是否开启沙箱
输出：exec_mode(fast|thinking|deep) + mode_reason（前端可见，AG-UI rag.mode_decision）
```

| requested | 意图信号 | 工具可用性 | exec_mode |
|---|---|---|---|
| auto | 简单单问 | 任意 | fast |
| auto | 复合 / 需交叉验证 | 有知识库或联网 | deep |
| auto | 复合 / 需交叉验证 | 无任何可用工具 | thinking（降级为多轮检索补查，不进工具循环） |
| fast | 任意 | 任意 | fast |
| thinking | 任意 | 有可用工具 | thinking |
| thinking | 强信号（显式深度/多源交叉失败） | 有可用工具 | deep |
| thinking | 任意 | 无可用工具 | thinking（仅检索+自答） |

**解析器实现要求**：

1. 纯函数、无 IO，可单测（输入三元组 → 输出二元组）；
2. 决策理由必须产出（`mode_reason`），前端展示「本次为什么用深度思考」；
3. 降级必须显式：工具不可用时不得进 deep（deep 模式没有工具可调，预算白白消耗）；
4. 用户显式选择的模式**不得被自动降级**（`fast` 用户请求不会被升级为 deep——自动升级只发生在 `auto`）。

### 2.3 兼容与入口收敛

- 旧请求体 `mode: "fast"|"thinking"|"auto"` 与新请求体 `agent_id` 双通道并存：
  - 带 `agent_id` → 直接使用该 Agent；
  - 只带 `mode` → 映射到内置 Agent（`fast`→`builtin_fast`，`thinking`/`auto`→`builtin_thinking`），再按 §2.2 解析 `exec_mode`；
- 既有 `deep_thinking: bool` 保留一个版本周期：`true` ≡ `mode=thinking` 且强信号 → deep；`false` ≡ `mode=auto`；下版本删除（过渡期在 API 层打 deprecation 头）。

## 3. 有界 ReAct 执行器

### 3.1 分层（通用件 / 业务件）

```text
module_agent/service/agent_runner.py   ← 业务无关的通用有界执行器（不感知任何业务工具）
        ▲ 注入：tools / system_prompt / ModeConfig / event_sink
        │
module_rag/service/deep_agent.py       ← 业务侧：构建工具、收集证据、融合排序
```

**通用执行器负责**（业务无关，不得出现任何具体业务名）：有界循环、模型调用与工具调用计数、墙钟截止、分步思考档位切换、工具结果回填、事件产出。
**业务侧负责**：注册哪些工具、把工具结果转成什么证据、如何排序、如何注入回答上下文。

### 3.2 AgentRunner 契约

```python
result = await agent_runner.run(
    messages=[...],                  # 已含 system prompt
    tools=[...],                     # BaseTool 列表（业务侧构建）
    cfg=ModeConfig(
        max_loops=6, max_model_calls=8, max_tool_calls=12, wall_clock_s=90,
        think_level_plan="high", think_level_answer="off",
    ),
    event_sink=...,                  # 过程事件下发（AG-UI）
)
# → AgentRunResult{status, stop_reason, messages, tool_calls, usage, events}
```

硬规则：

| 规则 | 说明 |
|---|---|
| 四重预算 | 任一触顶即优雅收尾并返回 `stop_reason`（`loop_budget`/`model_budget`/`tool_budget`/`timeout`），**不无限重试**（CA-12） |
| 墙钟每轮检查 | 循环内每轮开头比对截止时间，超时即停并输出已得证据 |
| 单工具超时 | 单次工具调用独立硬超时（默认 30s），超时按 `transient` 处理 |
| 分步思考档位 | **规划/选工具步骤**用 `think_level_plan`（high）；**理解工具结果/填参步骤**用 `think_level_answer`（off）；判定依据 = 最近一条消息是否为 `ToolMessage` |
| 结果回填 | 工具结果以 `ToolMessage` 回填，**不进用户可见对话流**；超长结果先截断预览 |
| 无工具降级 | 未注册任何工具时直接退化为单轮问答，不空转预算 |
| 事件可观测 | 每步产出事件（工具名 / 参数摘要 / 结果摘要 / 档位 / 耗时），供前端「思考过程」折叠展示 |

### 3.3 业务侧：工具构建与证据融合

| 工具 | 注册条件 | 说明 |
|---|---|---|
| `kb_search` | 会话命中知识库且有检索权限 | 结果进证据池，不进对话流 |
| `web_search` | 用户开启联网搜索 | 同上 |
| `run_script` | 沙箱已启用且配置完整 | 产出物进证据池 |
| Skill 句柄 | Skill `agent_callable=true` 且已发布 | 逐个注册为工具，工具名 = Skill key（`.`→`_`） |

证据处理链：

```text
工具结果 → _EvidenceCollector（kb_chunks / web_candidates / skill_outputs）
        → RRF 融合 → Rerank 精排 → knowledge_context_list + skill_context
        → 注入回答节点（循环外）→ 流式输出
```

- 回答节点在 ReAct 循环**之外**：循环只负责取证据，回答由独立节点流式产出，避免「边思考边吐字」把中间态当答案；
- Skill 输出格式化为 `skill_context` 单独注入（与检索证据区分，模型知道它是技能产物）。

### 3.4 与问答图的整合位置

```text
START → review(安全审计/意图) → resolve_mode(模式解析, 产出 exec_mode)
       → search ⇄ critic(充分性判定) → [exec_mode=deep] → deep(有界 ReAct)
       → source(溯源) → chat(回答节点, 流式) → END
```

- `resolve_mode` 节点 = §2.2 模式解析器的图内宿主；
- `deep` 节点 = §3.3 业务侧，注入 `AgentRunner`；
- `chat` 节点消费 `knowledge_context_list` / `skill_context` / `deep_events`，产出最终流式回答；
- checkpointer（PostgreSQL）承载会话状态，支持中断续跑（04 W-12 一致）。

## 4. 五拍协议：任务型 ai_agent 的执行规范

适用形态：`ai_agent` + `execution_strategy=plan_execute`（深度研究、批量报告、多步交付类任务）。对话问答类走 §3 的有界 ReAct，不需要清单。

### 4.1 总原则

| 层 | 做什么 | 不做什么 |
|---|---|---|
| 模型侧 | 分解、执行、交卷、按失败原因改单 | 不维护状态机、不做预算、不做权限、不写规则长文 |
| 运行时侧 | 记录事件、执行工具、验收、压缩、审批、预算、门控 | 不替模型思考、不每轮说教、不把内部状态灌进 prompt |

> **模型侧做减法，运行时侧做加法；约束事实（验收、权限、预算），不约束思考（步骤、工具、技能选择）。**

三个不可妥协项：**完成必须是验收事实**（模型自述不算）；**计划必须驱动取任务**（否则长任务必漂移）；**上下文必须一屏**（否则注意力被稀释）。

### 4.2 唯一数据对象

Todo / TaskPlan / Contract 三合一，只有一个任务对象，不存在三套状态同步：

```python
class Status(StrEnum):
    PENDING = "pending"
    DONE = "done"          # in_progress 由「第一项未完成」隐式表达，少一个状态少一类 bug

@dataclass
class Acceptance:
    kind: Literal["cmd", "artifact", "judge", "human"]
    spec: str                 # "pytest -q" / "report.md: sections>=3, citations>=5" / rubric
    def render(self) -> str:  # 模型只看到这一行
        return f"{self.kind}: {self.spec}"

@dataclass
class Item:
    id: str
    goal: str
    acceptance: Acceptance
    status: Status = Status.PENDING
    attempts: int = 0
    last_reason: str = ""      # 上次失败原因，重试时随任务回灌
    acceptance_hash: str = ""  # 防止执行者偷偷削弱验收

@dataclass
class Submission:
    artifacts: list[str]       # 产物路径：验收的第一取证对象
    evidence: list[str] = []   # 执行过的命令 / 关键输出

@dataclass
class Verdict:
    passed: bool
    reason: str = ""
    evidence: list[str] = []
```

落库：`agent_plan_item` 表（§7），运行期状态同时入 checkpointer，UI 从表投影。

### 4.3 两个动词与五条规则

模型新增动词只有两个（**运行时控制工具，不是 Skill**，不注册进业务 Skill 表，不进 `skill_invocation`）：

- `write_plan`：创建 / 替换 / 修订清单；运行时校验 schema、记录事件；
- `submit`：请求验收；**必须携带 `artifacts` 与 `evidence`**，否则验收无物可验。

写入 system prompt 的全部行为规则（五行）：

```text
1. 只做清单第一项未完成任务；动手前先确认它的验收标准。
2. 怎么做完全由你决定：步骤、工具、技能不限；用技能先看目录、再加载全文。
3. 做完调用 submit 交卷。完成与否由验收判定，你没有"完成"按钮。
4. 验收失败：按原因修复后重新交卷；同一项失败两次，必须先修改清单。
5. 清单可增删改，但验收标准只能加强、不能削弱；每次改动附一句原因。
```

**自主权边界**：分解自由、改单自由、执行自由；**唯一被收回的权利是「宣布完成」**。

### 4.4 唯一闸门（验收）

```python
async def verify(item: Item, submission: Submission, workspace: str) -> Verdict:
    """只看产物、证据与验收，不采信执行者自述。"""
    a = item.acceptance
    if a.kind == "cmd":
        code, out = await sh(a.spec, cwd=workspace)
        return Verdict(code == 0, out[-500:], [f"cmd:{a.spec}"])
    if a.kind == "artifact":
        ok, detail = await check_artifact(a.spec, submission.artifacts, workspace)
        return Verdict(ok, detail, submission.artifacts)
    if a.kind == "judge":
        # 干净上下文 + 只读 goal / 验收 / 产物 / evidence，不给执行者的思维链
        return await judge(item.goal, a.spec, submission, workspace)
    return await human_approval(item, submission)
```

四条硬规则：

1. **验收优先级**：`cmd` > `artifact` > `judge` > 主观描述；纯主观描述不允许创建，`judge` 必须带 rubric 并至少附一个客观产物检查；
2. **验收所有权**：验收标准归用户或策略层，模型可「加强」不可「削弱」，任何变更记录 diff；`acceptance_hash` 在失败后不变，verifier 拒绝「改验收过闸」；
3. **判官隔离**：judge 只见 goal / 验收 / 产物 / 必要 diff，不见执行者思维链与自述；
4. **交卷负载**：`submit` 必须带 `artifacts` 与 `evidence`。

验收器与 Skill 的关系：验收**不经过 SkillRuntime**（它不是业务能力，是事实判定）；但验收执行若调用了业务能力（如生成产物），该调用仍走 SkillRuntime 以留痕。

### 4.5 一屏上下文

模型每轮严格只看到：

1. 当前项全文：`goal` + `acceptance.render()` + `attempts` + `last_reason`；
2. 剩余项：每项仅标题一行；
3. 经验：关键词匹配 ≤3 行；
4. 技能目录：`name + description`，digest 变化才更新；
5. 最近一次 Verdict 的原因与证据引用。

**永不注入**：全量历史清单、每轮重复的规则说教、能力图谱、决策快照、完整 ReAct 转录。

硬 token 预算（建议 1.5k），裁剪顺序固定：

```text
当前项 > 验收标准 > 最近失败原因 > 剩余标题 > 经验 > 技能目录
```

**验收标准永不截断**；放不下先删剩余标题，再删经验——这本身就是「计划拆得太碎」的报警器。ReAct 轨迹压缩是运行时的事（保留最近 N 条工具结果，更早摘要化；摘要只作提示，**不作为验收事实**）。

### 4.6 唯一循环与静默守卫

```python
while (item := next((i for i in items if i.status is Status.PENDING), None)):
    if reason := guard.check(items):                 # 预算 / 重复哈希 / 取消
        return Report(items, stop_reason=reason)
    submission = await react(task=item, context=project_one_screen(item, items),
                             tools=skills.disclosed_tools())
    verdict = await verify(item, submission, workspace)
    if verdict.passed:
        item.status = Status.DONE
        continue
    item.attempts += 1
    item.last_reason = verdict.reason
    if item.attempts >= 2:                          # 两败必改单
        items = await plan.revise(goal, items, item, verdict)
        if plan.revisions > 3:                      # 改单也有上限
            return Report(items, stop_reason="replan_budget")
```

守卫三条，全是确定性代码，不花 token、不进 prompt：

1. **预算**：token、墙钟、工具调用数；全局预算 + 按剩余任务数计算的软配额；
2. **重复动作**：连续相同 `tool + normalized_args` 哈希超阈值即停（轮询类工具用 `wait` 显式豁免）；
3. **外部取消**：用户取消、审批拒绝、系统关闭。

两条静默规则：**两败改单**（同项失败两次必须拆分 / 换路径 / 换验收（只能加强）/ 升级人工；改单上限 3 次）；**无新产物守卫**（连续 N 次工具调用无新产物即停，不发进度提醒）。
失败原因前缀固定，仅一行：`[env]` 环境类（依赖缺失/网络不可用/权限不足）→ 换工具或升级人工；`[approach]` 方案类（方案不成立/实现错误）→ 改单或换路径。

### 4.7 一行经验（反思残影）

```text
情形 → 做法   [source: task-id]
```

只在 `verdict.passed` 后写；必须引用来源任务 id；关键词检索取前三行；只保留最近 N 条、可人工删除、相似去重；**不引入置信度、衰减、独立元循环**（样本不足时这些机制只是噪声）。

### 4.8 状态载体与观测

| 对象 | 载体 | 用途 |
|---|---|---|
| 清单（模型事实源） | checkpointer 状态 + `agent_plan_item` 表 | 运行期状态 / 断点续跑 / UI 投影 |
| 事件日志（系统事实源） | `skill_invocation` + `agent_job_run` + `agent_plan_event` | 回放、审计、恢复 |
| 验收事实 | `agent_plan_item.verdict_*` 字段 | 假完成率统计 |

> **系统的事实源是日志，模型的事实源是清单（日志的投影）。** 两者不需要同步协议，只需要单向投影。

### 4.9 北极星指标（只三个）

1. **假完成率趋零**：标记 done 但验收失败的比例；
2. **每成功任务成本不高于基线**：token / 工具调用 / 墙钟；
3. **任务成功率上升**：通过验收的任务比例。

其余指标（步数、重复动作率、改单次数、技能复用率、恢复成功率）只在北极星恶化时下钻。

### 4.10 按规模触发升级（复杂度不是禁止，但必须有信号）

| 触发信号 | 才引入的复杂度 |
|---|---|
| 技能目录超过上下文预算（约 50+ 条） | 检索 / 路由模型 |
| 任务真并行且共享资源 | 清单 → DAG + 依赖调度 |
| 同类任务反复出现，一行经验不够 | 技能固化 + 版本回归 |
| 高价值且可自动验证 | best-of-N / LATS |
| 不可信技能来源 / 多租户 | 签名、权限清单、沙箱 |
| judge 验收仍不可靠 | 独立 verifier 模型 / 过程奖励 |
| 长任务、崩溃恢复、合规审计 | checkpoint、决策快照、durable execution |

## 5. Skill / 知识库自动调用

### 5.1 tool-calling 清单按能力条件生成

对话 Agent 的工具清单**不静态列举**，由注册表在每次会话装配时生成：

```text
for skill in registry.published_skills:
    if not skill.agent_callable:            continue      # 04 §3.1 既有约束
    if not skill.visible_to(agent, ctx):    continue      # 权限：user_id / project_ids（CA-08）
    if not capabilities_available(skill):   continue      # 能力不足不注册（如无 embeddings 就不给向量检索）
    if skill.requires_联网 and not ctx.web_enabled: continue
    if skill.requires_沙箱 and not ctx.sandbox_ready:  continue
    tools.append(adapt(skill))                            # Manifest → tool schema
```

要点：

- **未注册 ≠ 不存在**：模型不会看到它没有的工具，避免「工具幻觉」；
- 知识库检索工具在**会话命中知识库**时才注册（`ctx.project_ids` 非空且用户有检索权限）；
- 工具名 = Skill key（`.`→`_`，04 W-7），Tool Adapter 闭包直持 Manifest，回查无损；
- 同一会话内工具清单**固定快照**（CA-09），避免运行期注册漂移。

### 5.2 自动升级链（意图 → 模式 → 工具集合）

```text
用户提问
  └─ 意图信号判定（复杂问 / 多源交叉 / 显式深度）
      ├─ 简单 → exec_mode=fast      → 工具集：仅轻量（无检索或单轮检索）
      ├─ 复合 → exec_mode=thinking  → 工具集：检索 + critic 补查
      └─ 强信号/补查失败 → exec_mode=deep → 工具集：检索 + 联网 + 沙箱 + 全部 agent_callable Skill
```

- 升级只发生在 `requested_mode=auto`；用户显式 `fast` 不升级（§2.2 规则 4）；
- 升级是**换执行模式**而非换 Agent：`deep` 仍由 thinking Agent 承载（§0 结论 1）；
- 升级事件下发前端（`rag.mode_decision`），用户可见「已切换到深度思考」。

### 5.3 知识库自动调用与权限

| 环节 | 规则 |
|---|---|
| 检索触发 | 意图判定命中「需要外部事实」→ 自动检索；或用户显式点名知识库 |
| 权限注入 | `project_ids` / `user_id` 由运行时注入，Skill 不可扩大（CA-08）；**AI 不得访问用户无权限的知识库** |
| 结果处理 | 检索结果进证据池（§3.3），不进对话流；不足由 critic 判定并补查 |
| 会话附件 | 走 04 §4.4 链路（interactive 优先级 + SkillRuntime 解析入库），附件产物自动可被后续轮次引用 |
| 引用 | 最终回答带溯源（`source_trace` 节点产出 `sources`），无证据支撑的结论要求模型标注不确定 |

### 5.4 失败反馈、熔断与降级

- **错误分类固定文案注入 ToolMessage**（04 W-10）：模型据此决定重试 / 换路 / 告知用户，不裸抛异常栈；
- **会话内 Skill 熔断**：同一 Skill 在本次会话连续失败 2 次 → 从工具清单摘除并下发 `skill_masked` 事件，避免死循环烧预算；
- **运行期版本固定**：Agent 发布时锁定 `skill_version_id`，会话内不再漂移（CA-09）；
- **幂等**：SkillRuntime 按 `idempotency.keys` 去重，重复调用复用既有 invocation（04 §4.5）。

## 6. 运维能力 Agent 化（`app_agent.py` 归位, 已更名 `app_host_probe.py`）

### 6.1 现状问题

`server_py/src/app_host_probe.py`（原 `app_agent.py`）是宿主机运维探针：挂 `docker.sock`，提供容器查看 / 启停 / 重启 / 克隆四类原语。问题：**直接操作 docker、绕过三层契约**——无 Skill 契约、无 `skill_invocation` 观测、无权限模型、无 Agent 编排、无幂等与取消语义；主服务侧只能按服务名约定硬编码调用。

### 6.2 目标结构（三层归位）

```text
Agent 层：ops_agent（static_agent，decision_mode=rule，agent_kind=job）
            steps: 探测 → 判定 → 执行 → 校验（线性 steps + when/skip_if 条件）
              │
              ▼ 编排（Skill 句柄，不直接碰 docker）
Skill 层：sys.container_list / sys.container_start / sys.container_stop
           sys.container_restart / sys.container_scale_up   （全部 static_skill）
              │
              ▼ 调用（HTTP，远端探针）
探针层：host_probe（探针进程, app_host_probe.py）——只暴露四类原语，按服务名过滤，Bearer 鉴权
```

| 能力 | 归属 | 说明 |
|---|---|---|
| 列出容器 | `sys.container_list`（static） | 走 Service 层封装 docker SDK |
| 启停 / 重启 / 克隆 | `sys.container_start` / `stop` / `restart` / `scale_up`（static） | 幂等键 = service + 目标容器标识 + 动作 |
| 伸缩与自愈编排 | `ops_agent`（static_agent） | 「心跳缺失 → 重启 → 仍缺失 → 扩容 → 校验」用 steps + when 表达 |
| 探针 HTTP 接口 | 部署形态 | 同镜像第二入口（与 `app_task.py` worker 同级），契约由 Skill Manifest 单一定义，主服务侧不再手写 HTTP 调用 |

要点：

- **主服务不直连任何宿主 docker**（既有安全边界保留）：探针只暴露最小原语集，按约定服务名过滤；
- **优雅摘除语义保留**：`stop` = SIGTERM 优雅停（warm shutdown），超时强杀后由 `acks_late + reject_on_worker_lost` 保证消息重投——该语义写在 Skill 的 `side_effects` 与运行时策略里，不再只存在于脚本注释；
- **人工停止与进程退出区分**：缩容用 `stop + remove`，滚动重启用 `restart`，既有语义原样保留（04 §3.1 的 `nature=static` 与幂等约定适用）；
- **可观测**：所有原语调用写 `skill_invocation`；`ops_agent` 运行写 `agent_job_run`，可查「谁在什么时候扩了容」。

### 6.3 探针进程定位

`app_agent.py` 不删除，但**降级为部署形态**：与 `app_task.py`（Celery worker）并列的同镜像入口，业务逻辑全部下沉到 Skill 与 Agent，主服务侧不再引用探针路径。文件保留原路径以免部署脚本失效，文件头注释更新为「探针入口：原语由 sys.container_* Skill 定义」。（后续命名修正：为避免与决策者 `ops_agent` 概念混淆，文件更名为 `server_py/src/app_host_probe.py`，compose 服务名同步由 `task_agent` 改为 `host_probe`。）

## 10. 评审定案与权衡记录（v1.0）

| 编号 | 议题 | 定案 | 否决的备选 | 理由 |
|---|---|---|---|---|
| W-16 | 问答模式如何建模 | **模式即 Agent**：`fast`/`thinking` 为内置对话 Agent（代码 Manifest 为事实源），`deep` 是 thinking Agent 内的升级执行模式，非第三个 Agent | ① 独立 `chat_mode` 配置表；② 继续用 `deep_thinking` 布尔开关 | 模式配置是「模型行为策略」，与 Agent 的提示词、工具集、预算同生命周期，分表必然漂移；`deep` 复用 thinking Agent 可避免三份近似 Agent 及其配置同步成本 |
| W-17 | 是否采用 langgraph prebuilt（`create_react_agent` / `TodoListMiddleware`） | **不采用**；LangGraph 只保留编排图 + checkpointer + interrupt（与 04 W-12 一致），ReAct 循环与清单协议自实现 | ① 直接用 `create_react_agent`；② 用 `TodoListMiddleware` 挂 todo | prebuilt 无法承载四重预算、分步思考档位、证据不进对话流、Skill 熔断与版本固定；`TodoListMiddleware` 的 todo 不驱动循环、模型易忘计划，且与「完成由验收判定」冲突（todo 是模型自述） |
| W-18 | 清单（todo）采用何种模型 | **采用「清单 = 任务对象」的唯一数据模型**（`Item`/`Acceptance`/`Submission`/`Verdict`），`write_plan`/`submit` 为运行时控制动词，验收是唯一闸门 | ① 通用 todo 列表（整表替换、模型自述完成）；② 完整 TaskPlan + todo 双状态 | 双状态必然同步出错；模型自述完成会让「假完成」不可观测；把「完成」收归验收是三个框架共同的盲点，本设计正面补上 |
| W-19 | `app_agent.py` 如何归位 | **收编为 Agent + Skill**：原语 → `sys.container_*` static_skill，编排 → `ops_agent`（static_agent），脚本降级为同镜像探针入口 | ① 保持独立脚本 + 主服务硬编码 HTTP 调用；② 拆成第四层「基础设施层」 | 游离脚本绕过 SkillRuntime 即失去观测 / 权限 / 幂等 / 配额；第四层与三层一等多公民原则冲突（04 CA-01） |
| W-20 | 自动调用如何受控 | **条件注册 + 意图升级 + 权限注入三重门控**：能力不足/无权限/未开启的工具不注册；升级仅在 `auto` 模式发生；`project_ids`/`user_id` 运行时注入不可扩大 | ① 全量工具常驻；② 由模型自行决定是否检索 | 全量常驻导致工具幻觉与 token 浪费；模型自决检索在无权限时会越界，违反 CA-08 与「AI 不得访问用户无权限的知识库」 |

## 11. 验收标准（REQ-019）

**批次 4**

- [ ] `mode=auto|fast|thinking` 三档请求均返回 `exec_mode` 与 `mode_reason`，前端可见决策理由；
- [ ] 用户显式 `fast` 不被自动升级为 deep；`auto` 在复合问题上自动升级到 deep；
- [ ] 无知识库 / 未开联网 / 沙箱未就绪时，对应工具不出现在 tool-calling 清单；
- [ ] 深度模式在墙钟 90s 或工具 12 次触顶时优雅收尾，返回已收集证据并给出 `stop_reason`；
- [ ] 规划步骤 `think_level=high`、工具结果回填步骤 `think_level=off`，可从事件流核对；
- [ ] 同一 Skill 在一次会话内连续失败 2 次后被摘除，并下发 `skill_masked` 事件；
- [ ] `sys.container_*` 调用写 `skill_invocation`；`ops_agent` 运行写 `agent_job_run`；
- [ ] 探针进程仍可独立部署，Bearer 鉴权与服务名过滤生效。

**批次 5**

- [ ] 清单由模型 `write_plan` 创建、运行时校验 schema，落 `agent_plan_item`；
- [ ] 验收失败两次触发强制改单，改单超过 3 次以 `replan_budget` 收尾；
- [ ] `acceptance_hash` 变化时 verifier 拒绝「改验收过闸」；
- [ ] judge 验收上下文不含执行者思维链与自述；
- [ ] 单轮上下文投影稳定在 1.5k token 预算内，且验收标准永不截断；
- [ ] 假完成率、成功任务成本、任务成功率三项指标可从 `agent_plan_item` + `skill_invocation` 统计。
