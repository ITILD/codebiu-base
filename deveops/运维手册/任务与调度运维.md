# 任务与调度运维
> 范围：异步任务队列（Celery worker）与周期调度（定时任务）的部署与日常管理。
> 关联需求：REQ-012（定时任务）、REQ-010（测试基线）、REQ-018（队列拆分）。

## 1. 架构总览
| 进程 | 组成 | 职责 |
| :--- | :--- | :--- |
| API | `python src/app.py` | 任务创建/投递 broker、状态查询（读库为主） |
| worker | `celery -A src.app_task worker` | 消费 `task_queue` 与 `q_interactive` 两队列执行任务（可多实例） |
| beat | `celery -A src.app_task beat` | 周期调度触发进程（需要定时任务时启动，全局单实例） |

- 所有后台任务（文档解析/重向量化/审计清理等）统一在 worker 进程执行，复杂解析不占用 API 进程
- broker/backend 在 `config.yaml` 的 `tasks` 段或 **系统配置 → 任务队列** 配置
  （生产配置 Redis；未配置时默认 `memory://`，消息不出进程，仅适合开发/测试）
- broker 地址变更需重启 worker 与 API

### 1.1 物理队列拆分与 q_interactive 独立 worker（REQ-018 批次 2）

任务投递按 priority 自动路由：**priority ≥ 7（会话交互类，如对话附件解析、SkillRuntime 的 interactive 调用）→ `q_interactive` 队列；其余 → `task_queue`**。目的：夜间批量任务积压不影响用户正在等待的交互任务。

部署形态二选一：

```bash
# 形态 A(默认/中小部署): 单 worker 同时消费两个队列(未设 WORKER_QUEUES 时的默认)
celery -A src.app_task worker

# 形态 B(高保障部署): 交互流量与批量物理隔离 —— 两个独立 worker 进程
WORKER_QUEUES=q_interactive celery -A src.app_task worker   # 交互专用(可多实例)
WORKER_QUEUES=task_queue   celery -A src.app_task worker    # 批处理专用(可多实例)
```

`WORKER_QUEUES` 环境变量覆盖监听队列（逗号分隔）；两队列共用同一 broker/backend 配置，升级无需改配置。

## 2. 进程启动
```bash
cd code/backend/server_py

# API 服务(投递 + 状态查询)
python src/app.py

# 任务执行进程(可多实例; Windows 建议 --pool=solo)
celery -A src.app_task worker

# 周期调度触发进程(需要定时任务时启动, 全局单实例)
celery -A src.app_task beat
```

worker 消费 `task_queue` 队列，由 Redis 分级子队列按任务 priority(0~9) 加权派发；beat 每分钟 tick 一次扫描到期调度。

### 2.1 Reaper 自愈线程（多实例免配置）
每个 worker 内置 Reaper 常驻线程：每 60s 重派发遗留 PENDING（消息丢失）并清扫僵尸 RUNNING（worker 崩溃/OOM 遗留，超 30 分钟无心跳置 failed）。多实例部署时经 Redis 分布式锁（`SET NX EX`，TTL 45s）竞争上岗，**同一时刻仅一个实例执行扫描**；持锁实例宕机后锁自动过期，其余实例下周期自动接管。所有副本统一启动即可，**无需区分谁开谁关**。

## 3. 定时任务（周期调度）

### 3.1 使用入口
后台 **任务队列 → 定时任务** 页面（权限码 `task:schedule:*`），或接口 `/task/schedules`。

- 触发方式二选一：5 字段 cron 表达式（`分 时 日 月 周`，分钟级精度）或固定间隔（秒，≥60）
- 调度定义落库（`task_schedule` 表）：新增/启停/改周期落库即热生效（下一分钟 beat tick 感知），无需重启
- 每次触发生成一条 `task_queue` 记录（执行历史在 任务列表 页按类型筛选），调度行回写"最近执行"快照
- 停机错过的触发**不补跑**（恢复时从当前时刻重算）

### 3.2 内置示例
首启自动播种 **审计日志周期清理**（任务类型 `sys_audit_purge`，每日 04:00，**默认停用**）：在定时任务页启用后，按 **系统配置 → 操作审计** 的保留期（`audit.retention_days`）周期清理过期审计记录。

### 3.3 调度开关
动态配置 `tasks.scheduler_enabled`（系统配置 → 任务队列）：控制 beat tick 是否派发（beat 启动时读取，修改后需重启 beat）。

## 4. 内存与体积设计（运维须知）
- **零新增依赖**：cron 为自研 5 字段解析器（`module_task/utils/cron.py`），不引入 croniter/APScheduler
- 执行历史不建关联表：调度行只存 `last_task_id/last_status`，完整历史即 `task_queue`，可由审计清理任务周期瘦身
- Web 进程不加载 celery 执行器（`import app` 可验证；仅投递时访问 celery 实例）

## 5. 日常巡检
| 检查项 | 方式 |
| :--- | :--- |
| 调度是否按期触发 | 定时任务页看"下次触发/最近执行"；连续 `dispatch_failed` 检查 worker/Redis |
| 任务积压 | 任务列表页统计卡片（pending 居高 → 扩 worker 实例） |
| 执行失败排查 | 任务详情 error 字段；worker/beat 进程日志 |
| beat 存活 | 需要周期任务时确认 beat 进程在运行（单实例）；长时间无触发检查 `scheduler_enabled` 与 beat 日志 |

## 6. 常见问题
**Q：改了 cron 多久生效？**
最迟 1 分钟（beat tick 扫描落库定义）。

**Q：beat 必须启动吗？**
仅在需要周期任务时启动，且全局单实例（多实例会重复触发，虽 `next_fire_at` 推进会自然收敛，仍建议单点）。

**Q：手动验证一个调度？**
定时任务页"立即触发"（`POST /task/schedules/{id}/trigger`），不影响周期节奏，生成任务可在任务列表查看。

**Q：worker 与 API 分开部署？**
可以。API（`app.py`）与 worker（`app_task.py`）可独立重启互不影响；定时任务管理页属 API 侧。

**Q：开发环境不想装 Redis？**
默认 `memory://` broker 下消息不出 API 进程、无独立消费者，任务会停留在 pending ——
适合只验证创建/查询/取消链路；要真实执行任务必须配置 Redis 并启动 worker。
