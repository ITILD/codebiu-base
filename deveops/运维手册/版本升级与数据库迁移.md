# 版本升级与数据库迁移（运维）
> 面向**已上线系统从版本 A 升级到版本 B**：结构跨版本转换、应用回滚、数据兼容。
> 迁移机制与脚本编写见 [server_py 04-数据库迁移](../../code/backend/server_py/doc/dev/04-数据库迁移.md)；首次部署见 [配置与数据库初始化](配置与数据库初始化.md)。

## 1. 版本对应关系
一次发布涉及三类版本，必须对齐：

| 对象 | 位置 | 说明 |
| :--- | :--- | :--- |
| 后端应用版本 | `code/backend/server_py/pyproject.toml` 的 `version` | 镜像 tag 来源 |
| 前端应用版本 | `code/frontend/vue3/package.json` 的 `version` | 注入 `__APP_VERSION__`、生成 `dist/version.json` |
| 数据库版本 | `alembic_version` 表 | 由 Alembic 脚本链决定 |

发布记录同时登记：后端 `doc/tag_doc/tag_<版本>.md`、前端 `doc/tag_doc/version_info.md`。

**原则**：数据库版本只向前演进；应用版本可以回滚，数据库结构回滚优先靠备份恢复。

## 2. 升级前检查
- [ ] 确认目标版本的迁移脚本已随代码提交（`alembic/versions/`）
- [ ] 确认版本链只有一个 head：`uv run alembic heads`
- [ ] 确认当前库版本：`uv run alembic current`
- [ ] 检查目标版本是否有破坏性变更（删表/删列/改类型/收紧 NOT NULL）
- [ ] 评估数据量：大表加列/建索引是否需要维护窗口
- [ ] 完成数据库备份（见 [数据库运维](数据库运维.md)）
- [ ] 完成前端 `dist` 备份（发布脚本通常自动备份）
- [ ] 准备回滚镜像 tag（至少保留上一个版本）

## 3. 标准升级流程（从版本 A 到版本 B）
```bash
# ① 记录当前状态
cd code/backend/server_py
uv run alembic current                 # 记为 A
uv run alembic heads                   # 确认唯一 head

# ② 备份
pg_dump -Fc -f backup_A_$(date +%F_%H%M).dump "$DB_URL"

# ③ 进入维护窗口：停写/停应用（单实例可直接停；多实例建议 nginx 返回维护页或摘流）

# ④ 部署版本 B 的代码与配置（先不启动）
#    - 后端代码/镜像
#    - config.prod.yaml（如有新增配置项）
#    - 前端 dist（可先切换静态资源）

# ⑤ 执行迁移（自动经过 A→A+1→…→B）
uv run alembic upgrade head

# ⑥ 校验
uv run alembic current                 # 应等于 heads
uv run alembic history | head

# ⑦ 启动版本 B 后端（生产建议 state.check_db=false）

# ⑧ 验证
curl -s http://127.0.0.1:6666/docs >/dev/null && echo OK
#    登录、核心 CRUD、权限、AI 流式、文件上传下载

# ⑨ 恢复流量，观察日志 30 分钟
```

要点：

- `upgrade head` 按 `down_revision` 链**依次执行所有中间版本**，无需逐版本手工执行。
- 迁移必须由**发布流程执行一次**；应用实例启动不升级，避免多 worker 竞争。
- 含结构变更的版本，先在预发/测试库用**生产数据副本**演练一次。

## 4. 多版本连续升级
```bash
# 例：线上 1.0.0，要升到 1.3.0
uv run alembic current          # 0001_baseline（或实际版本）
uv run alembic upgrade head     # 依次执行 0002、0003、…、head
```

跨版本注意：

1. **不要跳过中间脚本，也不要修改已发布脚本**（线上执行过的脚本视为只读，修正走新增版本）。
2. **应用版本与数据库版本配套**：记录每版要求的 `alembic` 版本，回滚时确认库仍兼容旧代码；一次只发一个版本，跨版本先预演。

## 5. 数据迁移（非结构变更）
`alembic revision --autogenerate` 只生成结构差异，**不生成数据回填**。数据转换时：

1. 新建迁移脚本，在 `upgrade()` 中手写 `op.execute(...)` 或分批 SQL；
2. 大数据量分批处理，避免长事务锁表；
3. 先可空/加默认值 → 回填 → 再收紧约束；
4. 为回填脚本准备校验 SQL（数量、空值、外键）；在预发环境用生产数据副本验证耗时与锁影响。

示例（分两步收紧非空）：

```python
def upgrade() -> None:
    op.add_column("user", sa.Column("status", sa.String(20), nullable=True))
    op.execute("UPDATE user SET status = 'active' WHERE status IS NULL")
    op.alter_column("user", "status", nullable=False)
```

## 6. 回滚策略
按优先级选择：

| 场景 | 做法 |
| :--- | :--- |
| 应用有问题、库结构兼容 | 回滚应用镜像/前端 dist，数据库保持新版本 |
| 库结构不兼容旧应用 | 恢复升级前备份，再回滚应用 |
| 迁移脚本有可靠 `downgrade()` | `uv run alembic downgrade -1`（仍需评估数据丢失） |
| 基线/破坏性变更 | **不要** downgrade 到空库；直接恢复备份 |

回滚后校验：

```bash
uv run alembic current
# 应用登录与核心链路
# 数据量与关键表抽样
```

## 7. 向量库 / 缓存 / 对象存储变更
| 组件 | 变更处理 |
| :--- | :--- |
| Milvus | 换实例或换 embedding 模型需**重建向量索引**（重新解析/向量化文档） |
| Redis | 换实例后缓存可重建；登录态/会话会失效 |
| S3（rustfs/MinIO） | 换桶/换端点需自行搬运对象数据后更新配置并重启 |
| 任务队列 | 任务统一经 Celery 派发；换 broker 需重启 API 与 worker |

这些变更**不在 Alembic 内**，需单独写入发布说明与回滚步骤。

## 8. 升级检查清单
- [ ] 备份完成且可恢复（抽样验证）
- [ ] `alembic heads` 唯一
- [ ] 迁移脚本经人工审查，含必要 `downgrade`
- [ ] 破坏性变更已评估/演练
- [ ] 维护窗口与停写已安排
- [ ] `upgrade head` 成功
- [ ] 应用启动日志无迁移/建表告警
- [ ] 核心链路验证通过
- [ ] 版本记录（前后端 tag_doc）已登记
- [ ] 回滚镜像与旧 dist 可用
